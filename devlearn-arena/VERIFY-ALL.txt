===========================================================================
全レッスンの通し確認と修正の指示
===========================================================================

【0】なぜこれをやるのか

自動のテストは全て通っていた。それでも、人が手で触っただけで次の 2 件が
見つかった（どちらも linux.b.04）。

  1. 正しいコマンドを打ったのに、エラー扱いになった
     （`grep -r timeout /var/log | wc -l` が 3 を返したのに、
       `Permission denied` の警告でエラーの案内が出た）
  2. 正しく打ったのに、達成にならなかった
     （「まだ達成した手順は無い」と出た。判定が、手で打つ答えの欄に
       依存していたため）

つまり「テストが通る」は「遊べる」ではない。同じ穴が他の分野にも残って
いる可能性が高い。

この指示書の目的は 1 つ。

  **全 131 本のレッスンを、人と同じ順序・同じ操作で最後まで通し、
    通らないものを直す。**

「ヒントの最後まで従ったのに達成にならない」レッスンは、全て不具合とする。


---------------------------------------------------------------------------
【1】1 本を人と同じように通す台本を作る
---------------------------------------------------------------------------

`tools/scenarios/verify-lesson.mjs` を作る。Playwright で、レッスン 1 本を
端から端まで操作する。レッスン ID を引数で受ける。

通る道筋は、人がやるのと同じにする。

  a. 都市の画面を開く
  b. 学習ライブラリからそのレッスンを開く
     （都市画面から入る道を通る。URL を直接叩いて画面だけ出すのは駄目）
  c. 解説を読み進める
  d. 理解の問いに全て正しく答える
  e. クイズに全て正しく答える
  f. 実戦を行う。**最後のヒントに書かれた操作だけ**を行う
  g. 結果の画面に進む
  h. まとめまで進む
  i. 都市の画面に戻る

正解は、レッスンの中身（`content/lessons/**`）から読む。台本の中に答えを
書き写さない。

実戦の操作は、実戦の型ごとに次のようにする。

  - 端末（端）: 最後のヒントのコマンドを、**1 文字ずつ打って Enter**。
                貼り付けで済ませない（人が打つのと同じ道を通す）
  - ドラッグ（sim-connect / sim-assign / sim-order）:
                mouse down → move → up の順で、実際にドラッグする
  - SQL / 設定の編集: 入力欄に打ち込んで実行する
  - 読み取り（sim-read）: 指示どおり選ぶ・押す

確かめること（1 つでも満たさなければ、そのレッスンは不合格）。

  - 結果の画面の「できたこと」に、達成条件の全ての手順が並ぶ
  - 「まだの手順」が空である
  - 正しい操作をしたのに、エラーの案内が出ていない
  - まとめまで進める
  - XP とスキルが増えている
  - 都市の画面に戻れる

【2】131 本すべてに流す
---------------------------------------------------------------------------

`tools/scenarios/verify-all.mjs` を作り、初回公開の範囲の 131 本に順に
流す。**失敗しても止めず、最後まで流す。**

1 本ごとに記録する。

  - 合格 / 不合格
  - 不合格なら、どの段階で止まったか（解説・理解・クイズ・実戦・結果・まとめ）
  - そこで何をしたか（打ったコマンド、ドラッグした物、選んだ答え）
  - 何が起きたか（画面の文、エラーの文）
  - その瞬間の画面の画像

結果を `docs/progress/verify-all.md` に表で書く。

  | レッスン | 結果 | 止まった段階 | した操作 | 起きたこと | 画像 |

**先に【1】【2】を終え、全体の合否（何本が不合格か）を書いてコミットしてから、
【3】の修正に入る。** 1 本直すたびに全体を流し直さない。


---------------------------------------------------------------------------
【3】不合格を直す
---------------------------------------------------------------------------

不合格を、原因ごとにまとめる。1 本ずつ直すのではなく、同じ原因のものは
一緒に直す。linux.b.04 の 2 件は、どちらも「原因が 1 つで、他の分野にも
同じ作りが残っている」種類だった。

想定される原因の型（これに限らない）。

  - 正しい操作なのに、警告や副作用でエラー扱いになる
  - 判定が、手で打つ答えの欄に依存している
  - 達成条件の式が、実際の模擬環境の状態と合っていない
  - ヒントの文が、その画面で実行できない形になっている
  - ドラッグの当たり判定が狭い・つかめない
  - 左の目的に出る名前と、右の画面に出る名前が違う

直す順は【2】の表で不合格が多い分野から。

1 件ごとに、`CLAUDE.md` 13 章のとおり **先に失敗するテストを書いてから**
直す。直した後、そのレッスンの `verify-lesson.mjs` を流して合格を確かめる。

分野を 1 つ終えるごとに、

  - `npm run typecheck` / `npm run lint` / `npm run test` / `npm run content:check`
  - `docs/progress/verify-all.md` の表を更新（結果を合格に書き換え、何を直したかを書く）
  - コミット


---------------------------------------------------------------------------
【4】ドラッグの実戦を目で確かめる
---------------------------------------------------------------------------

機械で通るだけでは足りない。ドラッグの実戦（sim-connect / sim-assign /
sim-order）は、画面を撮って次を確かめる。`REWORK-PRACTICE.txt` の原則 4。

  - つかんで動かせることが、見て分かる
  - 正しく置けば達成になる
  - 間違えた時、何が違うのかが 1 行で出る
  - やり直せる
  - 結果が動きで分かる（つないだ線を光が流れる・失敗は赤く光る）
  - `prefers-reduced-motion` では動きを止める

撮った画像と、確かめた結果を `docs/progress/verify-all.md` に足す。


---------------------------------------------------------------------------
【5】ゲームループを通しで確かめる
---------------------------------------------------------------------------

`tools/scenarios/loop.mjs` を作り、`docs/acceptance-criteria.md` の
G1〜G6 を 1 本の流れで確かめる。

  都市を表示 → 都市を操作 → 施設を選ぶ → レッスンを選ぶ
  → 解説 → 理解 → クイズ → 実戦 → 結果 → まとめ
  → XP / スキルが増える → 都市に戻ると変化が見える

この中に、**画面のリロードを 1 回挟む**。リロードしても進捗が消えないことを
確かめる（ブラウザ内の保存）。


---------------------------------------------------------------------------
【6】分かっている小さな不具合
---------------------------------------------------------------------------

実戦の「今打てるコマンドの候補」の行に、その実戦で使うコマンドが全て
出ていない。linux.b.04 では `wc` と `help` だけが出て、`grep` と `find` が
無かった。

候補の行は、**その実戦で使うコマンドを全て**出すようにする。全 131 本を
同じ目で見直す。


---------------------------------------------------------------------------
【7】進め方
---------------------------------------------------------------------------

  - 確認を求めず、止まるな
  - 動作の確認は `git push` と
    https://swallowsaba.github.io/swallow/devlearn-arena/ で行う。
    手元で `npm run dev` を動かす手順を書くな
  - 仕様書だけでは決められない事が出たら、`docs/decisions.md` の未決に
    「問題 → 影響 → 変更案」を書いてコミットし、`DECISIONNEEDED` とだけ
    出力して終われ
  - 全部終わったら `ALLDONE` とだけ出力して終われ
