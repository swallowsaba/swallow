===========================================================================
配信の流れを先に通す（push → 検査 → Cloudflare → 公開 URL）
===========================================================================

【0】目的

中身を作る前に、流れを通して証明する。

  コードを書く → GitHub へ push → GitHub Actions で検査
  → 通ったら Cloudflare へ配信 → 公開 URL で新しい物が見える

証明に使うのは小さなページ 1 枚と API 1 本だけ。
ゲームも学習も、この段では作らない。

今公開している物を止めない。今の GitHub Pages の配信（deploy.yml）
と devlearn-arena/ はそのまま残す。新しい流れは並べて作る。

---------------------------------------------------------------------------
【1】利用者が先に済ませること（Claude Code は手を出さない）
---------------------------------------------------------------------------

次は利用者本人がやる。Claude Code は、これが済んでいる前提で進める。
済んでいないために配信が失敗したら、何が足りないかを記録に書いて
DECISIONNEEDED で止まる。

1. Cloudflare のアカウント（無料）
2. API トークンを作る。
   必要な権限を、Cloudflare の公式の説明で確認して
   docs/deployment.md に書く（Workers の配信に要る物。
   静的アセットや Workers AI を使うなら、その分も）
3. GitHub のリポジトリの Secrets に登録する
   - CLOUDFLARE_API_TOKEN
   - CLOUDFLARE_ACCOUNT_ID

トークンと ID を、リポジトリの中・コミットの文・配信する物・
VITE_ の環境変数に書かない（指示書 41 章）。

---------------------------------------------------------------------------
【2】先に決めること
---------------------------------------------------------------------------

公式の今の情報を調べてから決める。古い知識で書かない。

- 静的な配信の形: Workers の静的アセットか、Pages か。
  - 推奨は Workers の静的アセット。1 つの Worker で、静的なページも
    API も MCP も同じ場所から出せる。別々にすると、間の通信の許可
    （CORS）と、2 つの配信の管理が要る
  - どちらにしたか、理由を docs/architecture.md に書く
- 無料枠: 1 日に使える量・制限・課金が始まる条件・
  超えたときに止まるのか課金されるのかを調べ、
  docs/free-services.md に書く（指示書 37 章）
- 課金が自動で始まる設定にしない
- 場所（URL）の形: 今は /swallow/devlearn-arena/ の下に各
  プロジェクトがある。新しい方の URL の形を決める
  （例: /devlearn/・/bus/）。独自ドメインを使うかも決める

---------------------------------------------------------------------------
【3】作る物
---------------------------------------------------------------------------

### 3.1 置き場所

新しい土台を web/ に作る。今の devlearn-arena/ には触らない。
web/ の中の細かい構成（共通の土台と、各プロジェクトの置き方）は、
この段では最小限にし、RESET-STACK.txt の段で決める。

### 3.2 最小のアプリ（証明のためだけの物）

- Svelte 5（runes）+ TypeScript（strict）+ Vite
- ページ 1 枚。次を表示する
  - 配信されたコミットの短い ID（どの版が出ているかを目で確かめる）
  - 組み立てた日時
  - /api/health を呼んだ結果
- 見た目は作り込まない。これは捨てる物ではなく、R1 の土台になる

### 3.3 API を 1 本

- GET /api/health が {"ok":true,"commit":"<短い ID>"} を返す
- 同じ Worker から出す（静的なページと同じ場所）

### 3.4 Cloudflare の設定

- wrangler の設定ファイル（wrangler.jsonc か wrangler.toml。
  公式の今の推奨を調べて選ぶ）
- 静的アセットの置き場所と、API の経路の振り分け
- 配信は GitHub Actions からだけ行う（手元から配信する手順を書かない）

### 3.5 GitHub Actions

今の deploy.yml を壊さない。別のファイルを足す。

検査（.github/workflows/ci-web.yml）

- web/** が変わった push と、web/** を触る PR で動く
- npm ci（lock が無ければ npm install）
- 型検査・lint・単体テスト・組み立て
- 4 つとも最後まで走らせ、落ちた物の中身を実行の「Summary」に出す
  （掘らなくても読める形にする）
- 秘密情報の検査

配信（.github/workflows/deploy-web.yml）

- main への push で動く
- 検査が通ったときだけ配信する
- wrangler で Cloudflare へ出す。トークンは Secrets から読む
- 配信した URL を、実行の Summary に出す

PR のプレビュー（任意。無料枠で可能か調べてから）

- PR ごとに一時の URL へ出す。無料枠を超えるなら作らない

### 3.6 記録

docs/deployment.md に、新しい流れを書く。

- 利用者がやること（【1】）と、その手順
- 流れの図（push → 検査 → 配信 → 公開）
- 失敗したときにどこを見るか
- 秘密情報の置き場所
- 手元で配信しないこと

docs/free-services.md に、【2】で調べた無料枠を書く。

---------------------------------------------------------------------------
【4】通ったと言える条件
---------------------------------------------------------------------------

次を全て満たしたら、この段は終わり。

1. main へ push すると、検査が走り、通ると配信される
2. 公開 URL を開くと、今 push したコミットの短い ID が出る
   （前の版が残っていない。キャッシュの扱いも確かめる）
3. /api/health が同じコミットの ID を返す
4. わざと型の誤りを入れて push すると、検査で止まり、配信されない
   （公開 URL は前の版のまま）。確かめたら元に戻す
5. 今まで通り、GitHub Pages の方の配信も動いている
   （https://swallowsaba.github.io/swallow/devlearn-arena/ が今まで通り）
6. 無料枠と課金の条件が docs/free-services.md に書かれている
7. リポジトリにも配信物にも秘密情報が無い（npm run secrets 相当）

4 番を実際にやって確かめること。「仕組み上そうなるはず」では通さない。

- 手元から Cloudflare へ配信する手順を書く
- トークン・アカウント ID をリポジトリ・配信物・VITE_ に書く

- 無料枠の数字を、調べずに書く
- この段でゲーム・学習の中身を作る

---------------------------------------------------------------------------
【6】進め方
---------------------------------------------------------------------------

  - 【2】を調べて決め、docs/decisions.md に短く記録してから作る
  - 小さく作って、1 つずつ push して確かめる
  - 記録は docs/progress/pipeline.md。
    決めたこと・調べた無料枠・【4】の 7 つをどう確かめたか・
    確かめた画面やログを書く
  - 確認を求めず、止まるな
  - 利用者がやること（【1】）が済んでいないために進めない場合は、
    何が足りないかを docs/progress/pipeline.md に書き、
    docs/decisions.md の未決にも書いて DECISIONNEEDED で止まる
  - 仕様書だけでは決められない事が出たときも同じく DECISIONNEEDED
  - 【4】を全て満たしたら ALLDONE とだけ出力して終われ
