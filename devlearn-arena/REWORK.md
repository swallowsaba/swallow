# 初心者が一から学べるようにする改修

**これは実装指示書である。上から順に実装し、終えた項目のチェックボックスを [x] に変えてコミットすること。**
各項目ごとに `npm run typecheck` `npm run lint` `npm run test` を通す。playwright は実行しない。
確認を求めず、報告のために止まらない。

## 背景（なぜ直すか）

現状は「すでに知っている人が確認するための道具」になっている。
初心者が一から学べるものにするのが目的。判断に迷ったら、**知識ゼロの人が独力で進めるか**を基準にする。

---

## 1. ヒントどおりにやれば必ず通るようにする

- [x] 1-1. `LessonStep` の `hints` の**最後の1件は、そのまま打てば手順を通過する完全なコマンド**にする。
  現在は「maxUnavailable を試そう」のような助言で終わっているものがあり、打っても進まない。
  複数コマンドが必要な手順は、最後のヒントを改行区切りの複数行にしてよい。

- [x] 1-2. **すべての任務・すべての手順について、最後のヒントを順に実行したらクリアできることをテストで担保する。**
  `src/engines/lesson/missions.test.ts` に追加する。既存の `play` ヘルパを使い、
  各手順の最後のヒントを改行で分割して順に実行し、`evaluate` が `cleared` になることを確かめる。
  このテストが落ちる任務は、ヒントか判定のどちらかが間違っているので直す。

- [x] 1-3. 判定が厳しすぎるものを緩める。
  「履歴に特定の文字列があること」を条件にしている手順があれば、状態を見る条件に置き換える。
  大文字小文字・余分な空白・引用符の有無で落ちないようにする。

## 2. 手順を飛ばせるようにする

- [x] 2-1. `LessonStep` に `solution: string[]`（模範解答のコマンド列）を必須で追加する。
  既存の全手順に、実際に通る解答を入れる。1-2 のテストは `hints` の代わりに `solution` を使ってもよい。

- [x] 2-2. 学習画面に「この手順を飛ばす」ボタンを置く。押すと `solution` を順に実行し、
  結果として手順が通過する。飛ばした手順は記録し、スコアから減点する（XP は据え置き）。
  「前の手順が終わっていないので次に進めない」で詰まる状態を無くすのが目的。

- [x] 2-3. 飛ばしたことを画面に残す（「この手順は解答を見ました」）。
  復習キューには必ず積む。

## 3. すべての任務に「学ぶ」段階を付ける

現在はいきなり課題から始まり、説明が無い。

- [x] 3-1. `LessonDefinition` に `intro` を追加する。

  ```ts
  intro: {
    /** 一行で言うと何か */
    summary: string;
    /** なぜこれを学ぶのか。現場で何に効くのか */
    why: string;
    /** 前提知識。知らなくても読めば分かる程度に噛み砕く */
    concepts: { term: string; plain: string }[];
    /** この任務で使うコマンドと、その意味 */
    commands: { command: string; means: string }[];
  }
  ```

- [x] 3-2. 任務を開くと、まず `intro` を全画面で表示する。「はじめる」を押すと課題に入る。
  一度読んだ任務は次から自動で開かない（設定で再表示できる）。

- [x] 3-3. 用語は**専門用語を使わずに説明する**。
  悪い例:「apply は desired state を etcd に保存し、controller が reconcile する」
  良い例:「apply は『こうなっていてほしい』という希望を書いて渡すこと。
  実際に作る作業は Kubernetes が裏で勝手にやってくれる」
  必要な専門用語は、初出で必ず `concepts` に平易な言い換えを載せる。

- [x] 3-4. 画面のどこでも、専門用語にマウスを乗せると平易な説明が出るようにする
  （`src/ui/Term.tsx` を作り、`concepts` の辞書を引く）。

## 4. Kubernetes を「作るところ」から始める

現在の k8s 任務は Deployment が既にある状態から始まり、確認するだけになっている。

- [ ] 4-1. `k8s/01/first-look` を作り直す。**ノードだけがある空のクラスタから始める。**
  手順は次の順にする。
  1. `kubectl get nodes` でクラスタに何があるか見る（Pod は0個であることを確認）
  2. `kubectl run web --image=nginx` で Pod を1つ作る（`kubectl run` を実装する）
  3. 時間を進めて Running になるのを見る
  4. `kubectl delete pod web` で消す。**作り直されないことを確認する**
  5. `kubectl create deployment web --image=nginx --replicas=2` で Deployment を作る
  6. Pod を1つ消す。**今度は作り直されることを確認する**
  7. なぜ違うのかを `intro` と `explain` で説明する

- [ ] 4-2. `kubectl run` `kubectl create deployment` `kubectl expose` を実装する。
  マニフェストを書かずに資源を作れるようにする（初心者は YAML から入れない）。

- [ ] 4-3. YAML はその次の任務にする。`kubectl get deploy web -o yaml` で
  さっき作ったものが YAML でどう表現されるかを見せてから、`kubectl apply -f` を教える。

- [ ] 4-4. 他のトラックも同じ観点で見直す。**既に出来上がった状態から始まる任務は、
  作るところから始まるように書き直す。** Git は `git init` から始まっているので概ね良い。
  Network は構成が与えられるのは仕方ないが、`intro` で構成図の読み方を説明する。

## 5. 右側の可視化を、任務ごとに変える・操作できるようにする

現在はタブが5つ並んでいるだけで、どの任務でも同じものが出る。中身も見て分かるものになっていない。

- [ ] 5-1. **任務の `track` に応じて、開いた瞬間から適切なタブを選ぶ。**
  git → 履歴、k8s → クラスタ、net → ネットワーク、github → PR、kernel → 村。
  関係ないタブは薄く表示するか隠す。

- [ ] 5-2. **可視化から操作できるようにする。**
  図の要素をクリックすると、対応するコマンドが**ターミナルの入力欄に流し込まれて実行される**。
  実行されたコマンドは端末に表示されるので、「この操作はこのコマンドだった」と結び付く。
  `TerminalHandle.submit(line)` が既にあるので、それを可視化コンポーネントに渡す。

  最低限つけるもの:
  - **クラスタ**: Pod をクリック → `kubectl describe pod <名前>`。
    Pod の「×」を押す → `kubectl delete pod <名前>`（消えて作り直される様子が見える）。
    ノードの「⏸」→ `kubectl cordon <名前>`。Deployment の ± → `kubectl scale`。
    「▶ 時間を進める」ボタン → `kubectl wait 5`。
  - **履歴（git）**: コミットをクリック → `git show <hash>`（実装する）。
    ブランチ札をクリック → `git switch <名前>`。
    「分岐して見る」→ `git switch -c <名前>`。
  - **ネットワーク**: 機器をクリック → その機器から `ping` を打つ。
    リンクをクリック → 切る／繋ぐ（`ip link set <dev> down` を実装する）。
    パケットが実際に線の上を流れるアニメーションを、`deliver` の hops から作る。
  - **PR**: チェックをクリック → `gh pr checks <番号>`。レビュー欄 → `gh pr review`。

- [ ] 5-3. **Kubernetes の可視化を作り直す。**
  現在はノードの箱に Pod が並ぶだけ。次を足す。
  - コントロールプレーン（apiserver / scheduler / controller / etcd）を図として出し、
    コマンドを打ったときに**どの部品が動いたかを光らせる**
  - Pod が配置されるとき、スケジューラからノードへ**飛んで着地する**動き
  - Deployment → ReplicaSet → Pod の所属を線で結ぶ
  - Service から Endpoints に載っている Pod にだけ線が伸びる。載っていない Pod には伸びない
  - 各 Pod に状態（Pending / Creating / Running / BackOff）を色と文字の両方で出す

- [ ] 5-4. **git の可視化を作り直す。**
  現在は縦一列。次を足す。
  - ブランチが分岐したら**横にずれて**別の列になる。マージで合流する
  - 3面（作業ツリー / インデックス / HEAD）を常時 3 レーンで表示し、
    `add` で真ん中へ、`commit` で右へ、ファイルが**動く**のを見せる
  - HEAD とブランチ名は札として、切り替えると**移動する**

## 6. 初心者向けの導線

- [ ] 6-1. 最初に開いたとき、どの任務から始めればよいかを迷わせない。
  推奨順を持たせ（`order: number`）、地図でも学習画面でも同じ順に並べる。
  未達成の前提任務があるものは「先に〇〇をやりましょう」と出す（ただし**遊べなくはしない**）。

- [ ] 6-2. 各任務の最後に「ここまでで分かったこと」を 3 行でまとめて出す。

- [ ] 6-3. 用語集の画面（`/glossary`）を作る。`concepts` を全任務から集めて一覧にする。

- [ ] 6-4. すべての文章を、専門用語を知らない人が読める日本語に直す。
  「宣言的」「冪等」「reconcile」のような語は、使うなら必ずその場で言い換えを添える。

## 守ること（変更しない方針）

- 出力をハードコードしない。状態機械から導出する
- エンジン層は React 非依存・決定論（`Date` と `Math.random` は禁止）
- エラーメッセージは本物に寄せる
- 失敗を罰にしない。HP や撤退は入れない
- UI は木枠・クリーム・金看板の外装
- 可視化は斜め45度にしない
- テストを必ず書く。任務は「解けること」をテストで担保する
