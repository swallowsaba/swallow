【0】なぜこれをやるのか

VERIFY-ALL.txt の確認は終わり、131 本が「最後のヒントに書かれた操作」で
通った（docs/progress/verify-all.md）。しかしそれは、1 本の道しか通って
いない。

人はヒントを開かない。自分の知っている書き方で打つ。正解を一度間違える。
小さい画面で遊ぶ。

実際に見つかった 2 件のうち 1 件目は、まさにこの種類だった。
grep -r timeout /var/log | wc -l は正しかったのに、Permission denied
の警告でエラー扱いになった。「ヒントの通りに打つ」確認では拾えない。

この指示書の目的は 4 つ。

  1. ヒントを開かず、別の正しい書き方で打っても達成になること
  2. 間違えた時に、次に何をすればよいか分かること
  3. 小さい画面でも遊べること
  4. ミッション 6 本が通しで遊べること

docs/progress/verify-all.md と同じ書き方で docs/progress/verify-free.md
に記録する。

【1】ヒントを開かず、別の書き方で通す
---------------------------------------------------------------------------

tools/scenarios/verify-free.mjs を作る。verify-lesson.mjs と同じ道を
通るが、次の 2 点が違う。

  - ヒントを一度も開かない
  - 実戦では、最後のヒントとは違う、しかし正しい操作を行う

### 別の正しい書き方をどこから持ってくるか

tools/scenarios/variants/<レッスンID>.json に、実戦の手順ごとに
2 通り以上の別解を書く。レッスンの中身（content/lessons/**）は変えない。
確認のための台本側の持ち物とする。

別解は、達成条件（CheckSpec）と模擬環境の状態から、「同じ結果に至る別の
道」として作る。実務でそう打つ人がいる書き方にする。例を挙げる。

  - grep -rc timeout /var/log ／ find /var/log -type f -exec grep -c timeout {} +
    （grep -r timeout /var/log | wc -l の別解）
  - ls -la ／ ls -al ／ ls --all -l（並びと書き方の違い）
  - kubectl get po ／ kubectl get pods（短い名前）
  - docker container ls ／ docker ps
  - systemctl status nginx.service ／ systemctl status nginx
  - 引数の順を入れ替えた物、引用符の有無が変わる物、絶対パスと相対パス

画面の操作（模）の別解は、順番の入れ替え（どの札を先に置いても達成になる）
と、置き場所の別の正解がある場合の両方を通す。

### 確かめること

1 本ごとに、次を全て満たさなければ不合格とする。

  - 別解の全ての通りで、全ての手順が達成になる
  - 正しい操作をしたのに、エラーの案内が出ていない
    （想定した失敗の手順は除く。docs/progress/verify-all.md の C2 の一覧）
  - ヒントを開いていないので、XP がヒント無しの満額で入る
    （docs/game-design.md 3 章。ヒントありの半分になっていたら不具合）
  - まとめまで進め、都市に戻れる

不合格は原因ごとにまとめて直す。CLAUDE.md 13 章のとおり、先に失敗する
テストを書いてから直す。

警告と失敗を混同していないかを特に見る。linux.b.04 の 1 件目と同じ形が
他に残っていないか。コマンドが目的を果たしたなら（終了の状態が 0、または
達成条件を満たしたなら）、途中の警告でエラーの案内を出さない。

【2】間違えた時の道
---------------------------------------------------------------------------

tools/scenarios/verify-wrong.mjs を作る。全 131 本で、わざと間違える。

### 理解・クイズ

各レッスンで、理解を 1 問・クイズを 1 問わざと誤答する。

  - 何が違うのかが出る
  - やり直せる
  - 正解すれば先に進める
  - XP が決まりどおり減る（docs/game-design.md 3 章。クイズの初回正解の
    分が入らないこと）
  - 画面が止まらない（pageerror が無い）

### 実戦

わざと間違ったコマンド・間違った置き方をする。CLAUDE.md 3 章の流れが
成立することを確かめる。

  エラー → エラー内容 → 原因候補 → ヒント → 再挑戦 → 成功

  - エラーの案内に、原因候補が出る
  - そこからヒントを開ける
  - やり直せる（失敗が行き止まりにならない）
  - 正しく打ち直せば達成になる

記録に、間違えた時に出た文をそのまま書く。その文を読んで、次に何をすれば
よいか分かるかを見る。分からない文は不具合として直す。

【3】1280x720 で確かめる
---------------------------------------------------------------------------

全 131 本と、ドラッグの 17 本。

【5】「想定した失敗」の 8 本を、人の目で見直す
---------------------------------------------------------------------------

docs/progress/verify-all.md の C2 で「想定した失敗（直さない）」とした
レッスンを、もう一度見る。対象は次の 8 本。

  git.b.06 ／ git.i.05 ／ git.i.02 ／ trouble.b.02 ／ docker.b.01 ／
  net.b.03 ／ net.i.01 ／ net.i.02

判定の基準を、作る側の都合から遊ぶ側の受け取り方に変える。

  エラーの案内が出た瞬間の画面を撮り、その画面だけを見て、
  「これは見るべきエラーだ」と分かるか。それとも「自分が間違えた」と
  思うか。

「自分が間違えた」と思う画面なら不具合とする。直し方は 2 つのどちらか。

  - 手順の目的の文に、失敗することを先に書く
    （k8s.b.01・net.b.04 で既にやった形）
  - エラーの案内の文を、「これは想定どおり。次はこれを見る」と分かる文にする

8 本それぞれについて、画面の文をそのまま記録に書き、どちらと判断したかと
理由を書く。

【7】進め方
---------------------------------------------------------------------------

  - 【1】から順に。1 つの段を終えるごとに
    npm run typecheck / npm run lint / npm run test /
    npm run content:check を流し、記録を書いてコミットする
  - 【1】【2】は先に全 131 本を流し、不合格が何本かを書いてコミットしてから
    直しに入る。1 本直すたびに全体を流し直さない
  - 確認を求めず、止まるな
  - 動作の確認は git push と
    https://swallowsaba.github.io/swallow/devlearn-arena/ で行う。
    手元で npm run dev を動かす手順を書くな
  - 仕様書だけでは決められない事が出たら、docs/decisions.md の未決に
    「問題 → 影響 → 変更案」を書いてコミットし、DECISIONNEEDED とだけ
    出力して終われ
  - 全部終わったら ALLDONE とだけ出力して終われ
