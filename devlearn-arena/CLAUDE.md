# CLAUDE.md — DevLearn FC

**このファイルは毎回の作業の最初に必ず読み、守る規則である。** 他のどの文書よりも優先する。

## 何を作っているか

Linux のシェル・Git・Kubernetes・ネットワーク・GitHub を、**サッカークラブの育成ゲーム**として学ぶ教材。
学習者はクラブのオーナー兼監督。**選手は覚えたコマンド**で、練習（レッスン）で育ち、
試合（障害対応）で試され、勝つと利用者が増え、**ホームタウンの街が育つ**。

- 読み手は用語を 1 つも知らない初心者。Pod も Kubernetes も知らない前提で書く
- 学ぶ中身は本物。コマンドは既存のエンジン（`src/engines/`）が本物の仕組みとして処理する
- 選手を動かすのは、必ず端末で打つコマンド。ボタンを押すだけで学習が進む作りにしない

## 正解の見本（最重要）

**`docs/design/mockups/` の 4 枚が正解の画面である。** 全ての画面は、この見本と同じデザイン言語で、
**同じ品質以上**で作る。見本より劣る画面は不合格。

| 見本 | 中身 |
|---|---|
| `office.html` | 事務所（日程・次の試合・施設・主力選手・スカウト・話題）と、街の表示（年の切り替え） |
| `squad.html` | 選手の札の一覧と、選手の詳細（能力の五角形・技・成長の記録） |
| `match.html` | 試合（端末・ピッチ・得点板・作戦ボード・実況・控え） |
| `hometown.html` | ホームタウン（育つ街と施設の名札、この 1 年で増えたもの、次の発展） |

見本はデザイン用の書式（`<x-dc>` と `renderVals`）で書かれており、**このリポジトリのブラウザではそのまま表示されない。**
中の要素と style の値を読み、見た目と構成を React で再現する。書式は写さない。
第 1 章で見本を画面として再現し、人が承認したものを `docs/design/baseline/*.png` に保存する。**以後の比較はその基準の画像と行う。**
人は見本の実物を https://claude.ai/artifact/8R55TEaqEgjKuhkTzRSxXB で見て、再現が正しいかを判断する。
街の絵は `docs/design/images/town1〜3.png`、その描き方は `docs/design/town-reference.py` にある。

デザインの数値は `docs/design/DESIGN.md`、ゲームの仕組みは `docs/game/GAME.md`、
選手と試合の一覧は `docs/game/CONTENT.md` に書いてある。作業の順番は `PLAN.md`。

## 層の境界（破らない）

```
src/engines/   仕組みの模型（シェル・Git・k8s・ネットワーク・GitHub）。既存。React に依存しない
src/game/      育成ゲームの模型（クラブ・日程・選手・施設・リーグ・街の成長）。純粋な TypeScript
src/town/      ホームタウンの描画（Canvas 2D）。src/game の状態を読むだけ
src/ui/        デザインの部品（tokens と共通部品）
src/screens/   画面（事務所・街・選手・施設・スカウト・リーグ・日程・練習・試合）
```

- `src/engines/**` と `src/game/**` は React・DOM・Canvas を import しない
- 画面は模型の状態を読み、操作は模型の関数を呼ぶだけ。画面に規則を書かない
- 乱数は seed から決める。`Math.random` と `Date` は使わない（既存の ESLint 設定が禁止している）

## デザインの決まり（機械で検査する）

- 色・文字・余白・角丸・影は **`src/ui/tokens.ts` の値だけ**を使う。値は `docs/design/DESIGN.md` の通り
- 生の色指定（`#` の 16 進、`rgb(`）と、トークン以外の文字の大きさは、`src/screens/**` と `src/ui/**` に書かない。
  テスト `src/__tests__/design-tokens.test.ts` で検査する
- 字体は 3 つだけ: 数字と英字の見出しは Barlow Condensed、日本語は Noto Sans JP、コマンドは JetBrains Mono
- 名札・吹き出しは互いに重ならず、建物や大事な情報を隠さない。部品 `src/ui/Pin.tsx` を使う
- 絵文字を絵として使わない。図は SVG か Canvas で描く
- 特定の市販ゲームの絵柄・名前・ロゴを写さない。エンブレムと施設は独自のもの

## 文章の決まり

- 感嘆符を使わない。芝居がかった台詞を使わない。実況は落ち着いたスポーツ中継の口調
- 用語は、練習の「登場」の段より前に出さない。出すときは平易な言い換えを必ず添える
- 画面の文字は日本語。コマンド名・オプション・ファイル名はそのまま

## 学びの流れ（練習＝レッスンは全てこの 5 段）

1. **体験**: コマンド無しで、その仕組みが無いと困る遊びをする（`docs/games/` の設計書の通り）
2. **登場**: 仕組みが施設や選手として現れる。用語はここで初めて出す
3. **確かめ**: 画面の中で答える問い（該当するものを押す、順に並べる）を 1〜2 問
4. **操作**: 端末でコマンドを打つ。各手順の前に「この操作で何を確かめるか」、後に「何が起きたか」を 1 行ずつ
5. **振り返り**: 選手の能力の伸びと、分かったことを 3 行で見せる

## 検証の決まり

1. `npm run typecheck` `npm run lint` `npm run test` を通してからコミットする
2. **見た目に関わる変更は、必ず撮影して PNG を自分で開いて見る。** `node tools/shoot.mjs <名前> <パス>`
3. **撮影は同時に 1 つだけ。** ブラウザを並べて立ち上げると、メモリ不足で強制終了される（Exit code 137）
4. 撮った画面を `docs/design/mockups/` と見比べ、劣る所があれば直してから完了にする
5. 新しい部品が本当に呼ばれているか（import され、画面に出ているか）を確かめる。存在するだけでは未完成
6. テストは振る舞いを確かめる（操作を与えたら状態がこう変わる）。部品があることだけを確かめるテストは書かない
7. 不具合は、先に再現する失敗するテストを書いてから直す

## 人の確認で止まる

- `PLAN.md` の各章の最後で `node tools/review.mjs` を実行し、確認ページ `review/index.html` を作る
- そして **`REVIEWNEEDED` とだけ出力して作業を止める**
- `REVIEW.md` の「承認する章」にその章の番号が書かれるまで、次の章に進まない
- `REVIEW.md` の「指摘」は最優先で直す。直したら「指摘」の該当行の先頭に `[済]` を付ける
