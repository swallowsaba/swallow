# CLAUDE.md — 開発の最上位ルール

このファイルは、Claude Code が**毎回の作業の最初に読み、常に守る**規則である。
他のどの文書よりも優先する。ここに書いたことを独自の判断で変えてはならない。

---

## 1. プロジェクトの目的

**「PC 向け都市開発シミュレーションゲーム」と「IT エンジニア育成」を一体にした学習ゲーム**を作る。

- 都市開発ゲームとしての体験が主軸。その中に本格的な IT 学習を組み込む
- IT 学習サイトをゲーム化するのではない。**IT エンジニアとして成長すると、都市が成長するゲーム**を作る
- 公開先は GitHub Pages。完全無料で動くこと

詳細: `docs/product-spec.md`

## 2. ゲームの基本コンセプト

```text
IT を学ぶ → 理解する → 実戦する → エンジニアとして成長 → スキル・XP 獲得
→ 施設・都市機能が発展 → 新しい学習領域が広がる → さらに IT を学ぶ
```

- 起動直後の主画面は**都市画面**。学習サイトのトップページではない
- 都市は上空から眺める 2.5D。道路で構成され、建物が並び、少しずつ発展する（Cities: Skylines II のような**体験と構造**を参考にする。見た目・UI・素材・コードは写さない）
- 建物を選ぶと情報パネルが開き、そこから関係する学習へ進める

詳細: `docs/game-design.md` `docs/city-design.md`

## 3. 学習システム

- **どの学習コンテンツからでも始められる。** 前提知識を学んでいないことを理由に学習を禁止しない
- 別に**推奨学習順**を示す。推奨はガイドであってロックではない（学習可能 ≠ 理解しやすい順序）
- 学習コンテンツは一本道ではなく**知識グラフ**。各コンテンツは推奨前提・関連・難易度・推奨順・次に学ぶとよい分野を持つ
- 1 レッスンの流れは **解説 → 理解 → クイズ → 実戦 → 結果・フィードバック → まとめ → XP / スキル**
- 初心者にいきなりコマンドを入力させない。最初に「何か・なぜ必要か・何に使うか・どんな場面で使うか」を説明する
- 専門用語には必ず説明を付ける。用語を押すと、簡単な説明・なぜ重要か・関連技術が見られる
- 失敗をゲームオーバーにしない。エラー → 内容 → 原因候補 → ヒント → 再挑戦 → 成功
- コンテナの概念を先に教え、Docker はその具体的な技術として扱う。Docker だけをコンテナ技術として扱わない
- Kubernetes は独立した重要分野として段階的に扱う。省略しない
- トラブルシューティングは独立した重要スキルとして扱う

詳細: `docs/learning-design.md` `docs/curriculum.md` `docs/content-spec.md`

## 4. 都市開発システム

- 都市には道路・建物・公園・オフィス・開発施設・サーバ施設・ネットワーク施設・データセンター・セキュリティ施設・研究施設などがある
- IT 分野と施設は対応する（Linux → サーバ施設 など）。**この対応は学習を制限するロックではない**
- 学習の成果で建物・施設・道路・都市機能・アップグレード・景観が発展する。小さな町から技術都市へ、見た目で分かるように変わる
- 都市の発展は一本道にしない。複数の技術分野のどれからでも発展できる

詳細: `docs/city-design.md` `docs/game-design.md`

## 5. UI/UX ルール

- **PC 向けゲーム。** 横長の画面が基本。スマートフォン向けに作らない
- **都市が主役。** 都市ビューをできるだけ広く取る。UI パネルが都市を覆い尽くしてはいけない
- 都市画面をダッシュボードにしない。カードを大量に並べるだけの画面にしない
- 学習の画面も、学習サイトに見えすぎないようにする（都市の施設の中で学んでいる体裁）

詳細: `docs/ui-design.md`

## 6. ビジュアルルール

- フォントは `docs/visual-design.md` の指定のみ。ブラウザの標準フォントをそのまま使わない
- 建物は奥行き・側面・屋根・窓・外観の細部・道路との接続・周辺環境を持つ。**四角形＋三角形だけの建物は禁止**
- 建物・主要アイコンに絵文字を使わない
- 建物は自作 SVG か、ライセンスが明確な無料素材で作る。単純なプレースホルダーを完成版にしない

詳細: `docs/visual-design.md` `docs/asset-policy.md`

## 7. 技術ルール

- 技術は必要最小限。採用理由は `docs/architecture.md` に書く。新しい依存を足すときは、同じ文書に理由を追記してから足す
- コンテンツ（レッスン・クイズ・実戦・用語・施設・ミッション）は**データ**として持ち、アプリ本体を改修せずに追加できるようにする
- 模擬環境（端末・Git・コンテナ・Kubernetes・ネットワーク・HTTP・DB）は React に依存しない純粋な TypeScript で作り、テストする
- 乱数は seed から決める。同じ操作からは同じ結果になる

詳細: `docs/architecture.md` `docs/data-model.md`

## 8. 無料利用ルール

有料サーバ・有料 API・従量課金 API・有料 DB・有料 SaaS・有料 AI API・有料素材を**前提にしない**。
AI が無くても基本のゲームと学習が成立すること。

詳細: `docs/free-services.md`

## 9. GitHub Pages ルール

- 最終公開先は GitHub Pages。静的ファイル（HTML・CSS・JS/TS・SVG・静的 JSON・ブラウザ API）で動くことを優先する
- 保存は localStorage と IndexedDB を使う
- サブディレクトリ配信（`/swallow/devlearn-arena/`）と直リンクの両方で動くこと

詳細: `docs/deployment.md`

## 10. Cloudflare ルール

- **Workers を使うこと自体を目的にしない。** GitHub Pages だけで実現できるものは Pages で実装する
- サーバ側の処理がどうしても必要な場合だけ使う。無料枠の範囲に収める
- 使う前に、公式情報で無料枠・制限・課金条件を確認し、`docs/free-services.md` に日付付きで記録する

## 11. セキュリティルール

- API キー・パスワード・秘密鍵・Cloudflare の秘密情報・GitHub Token などを**絶対にコミットしない**
- GitHub Pages に秘密情報を置かない。秘密は GitHub Secrets か Cloudflare の Secrets に置く
- コミットの前に秘密情報が含まれていないか確かめる（`docs/testing-strategy.md` の検査を通す）

## 12. 開発 Phase

`docs/development-plan.md` の Phase を順番に進める。**一度に全部を作らない。**

```text
仕様確認 → 小さく実装 → 起動 → テスト → 画面確認 → 修正 → 次の Phase
```

- 各 Phase の完成条件を満たすまで次に進まない
- 各 Phase の終わりに、完成条件・テスト・視覚確認の結果を `docs/progress/phase-<番号>.md` に記録してから次へ進む
- Git は意味のある単位でコミットする。大きな変更を一度に入れない

## 13. テストルール

- `npm run typecheck` `npm run lint` `npm run test` を通してからコミットする
- **UI は「動いた」だけで完成にしない。** 画面を撮影し、画像を自分で開いて、`docs/visual-design.md` の視覚確認の項目を 1 つずつ確かめる
- 撮影の方法は `docs/testing-strategy.md` 6 章
- テストは振る舞いを確かめる。部品が存在するだけを確かめるテストは書かない
- 不具合は、先に再現する失敗するテストを書いてから直す

詳細: `docs/testing-strategy.md`

## 14. 仕様変更ルール

- **根拠は仕様書だけ。** 仕様書に無い機能・画面・要素を、ほかの経緯（以前の指示書・以前の実装・一般的なゲームの慣習）から持ち込まない

- 重要な仕様を**勝手に変更・削除・簡略化・置換しない**
- 仕様書と実装が食い違う、または仕様どおりに作れない場合は、次の形で報告し、`docs/decisions.md` の「未決」に書く。判断が出るまで、その仕様に関わる変更をしない

```text
問題 → 影響 → 変更案（複数あれば並べる）
```

- 要求同士が食い違う場合は、片方を消さず、両立案を設計して `docs/decisions.md` に書く

## 15. 禁止事項（絶対に行わない）

- 学習サイト風の UI にする / 古いウェブサイト風の UI にする / 管理画面風の UI にする
- Bootstrap そのままのデザイン / 標準ブラウザフォント / 青いリンクを大量に並べる
- カードを大量に並べるだけ / 四角いボタンを大量に並べるだけ / スマホゲーム風 UI
- 都市画面をダッシュボードにする / 都市を単なる背景にする / 都市が UI に埋もれる
- 四角＋三角だけで建物を作る / CSS の図形だけで都市を作る / 絵文字で建物やアイコンを作る
- Dockerだけを「コンテナ技術」として扱う / Kubernetes を省略する
- 学習を一本道にする / 前提知識が無いと学習できないロックを作る
- いきなりコマンドを入力させる / 用語を説明せずに進める
- XP を稼ぐだけのゲームにする
- 有料 API・有料サーバを必須にする / 秘密情報を GitHub に置く
- Cities: Skylines II の UI・画像・建物・モデル・アセット・コード・固有デザインを写す
- 重要な仕様を勝手に変える / 一度に全機能を実装する / 動くだけで完成と判断する
