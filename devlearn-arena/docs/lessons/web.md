### web.b.01 URL の組み立て（URL・初級）
- 解説: 何か=Web 上の資源の住所。スキーム・ホスト・ポート・パス・クエリからなる ｜ なぜ=どこの何を、どの方法で取るかを 1 行で正確に示す ｜ 何に=リンク・API の呼び出し ｜ 場面=共有された URL が開けない
- 図: https://shop.example:8443/items?id=3 を部品ごとに色分け
- 理解: [図] 部品の名前を当てる ／ [関係性] ホストと DNS → 名前を IP に変えてから接続
- クイズ: [用語] ? の後 → クエリ ／ [結果予測] ポートを省いた https → 443 ／ [原因特定] パスの綴りの誤り → 404 になりやすい
- 実戦（端）: 目的=依頼文（shop.example・https・8443・/items・id が 3）から URL を組み立て、curl で取り出す ／ 達成=①一覧（/items）の数（4）②クエリ ?id=3 で取れた商品の名前（灯台の模型）を答える ／ ヒント=①部品の順と区切りの記号 ②ポートが既定（443）でない ③curl "https://shop.example:8443/items?id=3" ／ エラー=Failed to connect … port 443→原因候補「ポートの書き忘れ」、plain HTTP request was sent to HTTPS port→原因候補「スキームを http にした」、404→原因候補「パスとクエリの取り違え」
- 結果: 成功=部品から URL を作れた ／ 未達=部品の違いを示す
- まとめ: ①URL は部品の組み合わせ ②既定のポートは省ける ③ホストは DNS で引かれる ／ 次: web.b.02

### web.b.02 リクエストとレスポンス（HTTP・初級）
- 解説: 何か=依頼（リクエスト）と返事（レスポンス）の決まった書式 ｜ なぜ=ブラウザもアプリも同じ決まりで Web とやり取りする ｜ 何に=全ての Web と API ｜ 場面=ブラウザでは見えるのにプログラムでは取れない
- 図: GET /items HTTP/1.1 と、200 OK・ヘッダ・本文
- 理解: [並べ替え] 接続 → 依頼 → 返事 ／ [図] 依頼の 1 行目の各部分を押す
- クイズ: [用語] レスポンスの最初の数字 → ステータスコード ／ [結果予測] curl -i → ヘッダと本文 ／ [状況判断] 返事の見出しだけ見る → curl -I
- 実戦（端）: 目的=curl で依頼を送り、返事の数字と種類（Content-Type）を答える ／ 達成=両方正しい ／ ヒント=①curl ②見出しも表示 ③curl -i http://shop.example/ ／ エラー=Could not resolve host→原因候補「ホスト名の誤り」
- 結果: 成功=やり取りを読めた ／ 未達=依頼と返事を並べる
- まとめ: ①HTTP は依頼と返事 ②返事は数字・見出し・本文 ③curl で確かめる ／ 次: web.b.03, web.b.04

### web.b.03 HTTP メソッド（メソッド・初級）
- 解説: 何か=依頼の種類（GET 取る・POST 作る・PUT 置き換える・DELETE 消す） ｜ なぜ=同じ URL でも何をしたいかを伝える ｜ 何に=フォーム送信・API ｜ 場面=取るつもりで消してしまう事故
- 図: 1 つの資源に対する 4 つの操作
- 理解: [用語] メソッドと操作を結ぶ ／ [はい・いいえ] GET で状態を変えるのがよい → いいえ
- クイズ: [選択] 新しく作る → POST ／ [状況判断] 何度送っても同じ結果になる物 → GET・PUT・DELETE ／ [原因特定] 405 → そのメソッドを受け付けていない
- 実戦（端）: 目的=商品を 1 つ作り、取り、消す ／ 達成=作成・取得・削除が記録される ／ ヒント=①順番 ②-X でメソッド ③3 つのコマンド ／ エラー=405→原因候補「メソッドの誤り」
- 結果: 成功=操作を使い分けた ／ 未達=送ったメソッドを示す
- まとめ: ①メソッドは依頼の種類 ②GET で変えない ③405 はメソッドの誤り ／ 次: web.i.01

### web.b.04 ステータスコード（ステータス・初級）
- 解説: 何か=サーバの返事の種類を表す 3 桁の数 ｜ なぜ=何が起きたかを機械も人も判断できる ｜ 何に=障害の切り分け・API の処理の分岐 ｜ 場面=画面が真っ白
- 図: 2xx 成功・3xx 転送・4xx 依頼側・5xx サーバ側
- 理解: [図] 例を 4 つの箱に仕分ける ／ [はい・いいえ] 4xx はサーバの故障 → いいえ
- クイズ: [用語] 404 と 403 → 無い／禁止 ／ [状況判断] 503 で最初に疑う → 後ろのサーバの停止や過負荷 ／ [結果予測] 存在しないパス → 404
- 実戦（端）: 目的=3 つの URL のうち壊れている物を見つけ、原因の側を答える ／ 達成=正しい組み合わせ ／ ヒント=①見出しだけ ②4xx と 5xx ③答え ／ エラー=取り違え→原因候補「302 を失敗と見た」
- 結果: 成功=数字から原因の側を判断できた ／ 未達=数字の分類を示す
- まとめ: ①4xx は依頼側 ②5xx はサーバ側 ③3xx は転送 ／ 次: web.b.05, trouble.i.03

### web.b.05 HTTP ヘッダ（ヘッダ・初級）
- 解説: 何か=依頼と返事に付く追加の情報 ｜ なぜ=本文の種類・保存の仕方・転送先などを伝える ｜ 何に=キャッシュ・転送・認証 ｜ 場面=画像が文字として表示される
- 図: Content-Type・Cache-Control・Location・Set-Cookie の例
- 理解: [用語] ヘッダと役割を結ぶ ／ [状況説明] 画像が文字になる原因の見出しを選ぶ
- クイズ: [原因特定] 画像が文字で出る → Content-Type の誤り ／ [結果予測] 301 と Location → その先へ移る ／ [状況判断] 保存させたくない → Cache-Control: no-store
- 実戦（端）: 目的=返事の見出しから、転送先と保存の決まりを答える ／ 達成=両方正しい ／ ヒント=①-I ②Location と Cache-Control ③答え ／ エラー=見つからない→原因候補「本文を見た」
- 結果: 成功=見出しを読めた ／ 未達=該当の行を示す
- まとめ: ①ヘッダは追加の情報 ②種類・保存・転送 ③見出しだけ見るなら -I ／ 次: web.b.06, web.i.04

### web.b.06 Cookie とセッション（状態・初級）
- 解説: 何か=ブラウザに預ける小さな札（Cookie）と、サーバ側で利用者を覚える仕組み（セッション） ｜ なぜ=HTTP は 1 回ごとに独立しており、ログイン状態を覚えられない ｜ 何に=ログイン・カート ｜ 場面=ページを移るとログアウトしてしまう
- 図: ログイン → Set-Cookie → 以後の依頼に Cookie → サーバが利用者を特定
- 理解: [並べ替え] 札を受け取って使う流れ ／ [はい・いいえ] Cookie に暗証番号をそのまま入れてよい → いいえ
- クイズ: [用語] セッション ID → 利用者を特定する札の番号 ／ [原因特定] 移るとログアウト → Cookie が送られていない ／ [状況判断] 盗まれにくくする → Secure と HttpOnly
- 実戦（模）: 目的=ログイン状態が保たれない原因を見つけて直す ／ 達成=移ってもログインのまま ／ ヒント=①札を受け取っているか ②送り返しているか ③Cookie の範囲（パス）の設定 ／ エラー=まだ切れる→原因候補「範囲が狭い」
- 結果: 成功=状態の保ち方を理解した ／ 未達=札の流れを示す
- まとめ: ①HTTP は覚えない ②Cookie で札を預ける ③札に安全の印を付ける ／ 次: sec.b.02

### web.b.07 Web サーバの役割（Web サーバ・初級）
- 解説: 何か=依頼を受けてファイルや結果を返すプログラム ｜ なぜ=サイトを公開するには、依頼を待ち続ける者が要る ｜ 何に=サイトの公開・後ろのアプリへの中継 ｜ 場面=作ったページを公開したい
- 図: 依頼 → Web サーバ → 公開用のディレクトリのファイル → 返事
- 理解: [関係性] 公開用のディレクトリと URL のパスの対応 ／ [はい・いいえ] 公開用ディレクトリの外のファイルも見える → いいえ
- クイズ: [結果予測] /about.html の依頼 → 公開用ディレクトリの about.html ／ [原因特定] 403 → 読む権限が無い ／ [状況判断] 起動したのに届かない → 待ち受けとポート
- 実戦（端）: 目的=模擬サーバで index.html を公開する ／ 達成=/ で 200 と本文 ／ ヒント=①置く場所 ②サーバを動かす ③ファイルを置いて起動 ／ エラー=403→原因候補「権限」、404→原因候補「置き場所」
- 結果: 成功=ページを公開できた ／ 未達=置き場所とパスの対応を示す
- まとめ: ①Web サーバは返事をする係 ②公開用ディレクトリとパスが対応 ③403 は権限、404 は場所 ／ 次: web.b.08, web.i.03

### web.b.08 HTTPS（HTTP を安全にする）（HTTPS・初級）
- 解説: 何か=HTTP を TLS で包んだもの。443 番を使う ｜ なぜ=途中で読まれたり書き換えられたりしないため、相手が本物か確かめるため ｜ 何に=全ての公開サイト ｜ 場面=http のページに「保護されていない」と出る
- 図: http（中身が見える）と https（包まれて見えない）の比較と、http から https への転送
- 理解: [関係性] HTTPS と TLS → HTTP を TLS で包む ／ [状況説明] 混在コンテンツ（https のページに http の画像）の何が問題か
- クイズ: [選択] 既定のポート → 443 ／ [状況判断] http で来た利用者 → https へ転送（301） ／ [原因特定] 鍵の印に警告 → ページの中に http の部品
- 実戦（端）: 目的=http の依頼を https へ転送し、混在している画像を https に直す ／ 達成=http が 301 で https へ、警告なし ／ ヒント=①転送の設定 ②ページ内の http の参照 ③転送の 1 行と画像の URL の修正 ／ エラー=転送が繰り返す→原因候補「https からも転送している」
- 結果: 成功=サイトを安全にできた ／ 未達=警告の原因の部品を示す
- まとめ: ①HTTPS は包んだ HTTP ②http は https へ転送 ③部品も全て https に ／ 次: sec.b.07, web.a.01

### web.i.01 REST と API（API・中級）
- 解説: 何か=プログラムどうしが Web でやり取りする窓口（API）と、資源と操作で設計する考え方（REST） ｜ なぜ=画面を通さずにデータをやり取りし、組み合わせる ｜ 何に=スマホアプリ・外部サービスとの連携 ｜ 場面=在庫を別のシステムから取りたい
- 図: /items と /items/3 に対する 4 つのメソッドの表
- 理解: [図] 表の空欄を埋める ／ [関係性] 資源と URL・操作とメソッド
- クイズ: [状況判断] 3 番の商品を消す → DELETE /items/3 ／ [原因特定] 400 → 送った中身の形が違う ／ [結果予測] POST /items が成功 → 201 と新しい資源の場所
- 実戦（端）: 目的=在庫 API で商品を探し、数を更新する ／ 達成=数が更新されている ／ ヒント=①一覧から ID ②更新のメソッド ③GET と PUT のコマンド ／ エラー=400→原因候補「JSON の形の誤り」
- 結果: 成功=API を使えた ／ 未達=依頼と返事を並べる
- まとめ: ①API はプログラムの窓口 ②資源は URL・操作はメソッド ③失敗は数字で分かる ／ 次: web.i.02, web.a.03

### web.i.03 仮想ホストとリバースプロキシ（Web サーバ・中級）
- 解説: 何か=1 台で複数のサイトを出し分ける仕組み（仮想ホスト）と、後ろのアプリに中継する仕組み（リバースプロキシ） ｜ なぜ=入口を 1 つにして、後ろを入れ替えやすくする ｜ 何に=複数サイトの同居・アプリの公開 ｜ 場面=api.example を後ろのアプリにつなぎたい
- 図: 入口の Web サーバが名前で振り分け、/api を後ろのアプリへ中継
- 理解: [関係性] 名前で振り分ける・パスで中継 ／ [状況説明] 後ろが止まった時の返事（502）
- クイズ: [原因特定] 502 → 後ろのアプリに届かない ／ [状況判断] 2 つのサイトを 1 台で → 名前で振り分け ／ [結果予測] 中継先の綴りの誤り → 502
- 実戦（編）: 目的=shop.example は静的ファイル、api.example は後ろのアプリへ中継するよう設定する ／ 達成=両方とも 200 ／ ヒント=①名前ごとの設定 ②中継の設定 ③完成した設定 ／ エラー=502→原因候補「後ろのポートの誤り」
- 結果: 成功=入口で振り分けられた ／ 未達=どの設定に当たったかを示す
- まとめ: ①名前で出し分ける ②中継で後ろへ ③502 は後ろに届いていない ／ 次: sec.i.02, k8s.i.04

### web.i.04 キャッシュ（性能・中級）

### web.i.05 CORS（安全・中級）
- 解説: 何か=ブラウザが、別のサイトへのデータの取得を既定で止める決まりと、その許し方 ｜ なぜ=悪いサイトが利用者の権限で勝手にデータを取らないため ｜ 何に=画面と API が別の場所にある構成 ｜ 場面=画面から API を呼ぶとブラウザでだけ失敗する
- 図: 画面のサイト → 別のサイトの API。返事の許可の見出しが無いと止まる
- 理解: [はい・いいえ] CORS はサーバが通信を止める仕組み → いいえ（ブラウザが止める） ／ [関係性] 送り元のサイトと許可の見出し
- クイズ: [原因特定] curl では取れるがブラウザで失敗 → CORS ／ [状況判断] 自分の画面だけ許す → 送り元を指定して許可 ／ [選択] 全てを許す * の危険 → 誰でも使える
- 実戦（模）: 目的=自分の画面のサイトだけに API の利用を許す ／ 達成=自分の画面で成功、他では止まる ／ ヒント=①許可の見出し ②送り元を絞る ③設定の 1 行 ／ エラー=まだ止まる→原因候補「送り元の綴り」
- 結果: 成功=必要な所だけ許した ／ 未達=ブラウザの判断を示す
- まとめ: ①止めるのはブラウザ ②サーバが許可を返す ③許す範囲を絞る ／ 次: web.a.03

### web.i.06 HTTP/2 と HTTP/3（版・中級）
- 解説: 何か=1 本の接続で並行してやり取りする HTTP/2 と、UDP の上で動く HTTP/3 ｜ なぜ=多くの部品を持つページを速く読み込む ｜ 何に=今の Web ｜ 場面=部品の多いページの読み込みが遅い
- 図: HTTP/1.1（順番待ち）と HTTP/2（並行）の比較
- 理解: [関係性] HTTP/3 と UDP ／ [はい・いいえ] 版が変わると URL の書き方も変わる → いいえ
- クイズ: [結果予測] 部品 50 個のページ → HTTP/2 の方が待ちが少ない ／ [用語] 多重化 → 1 本で並行 ／ [状況判断] 対応しているか確かめる → 返事の版を見る
- 実戦（端）: 目的=サイトが使っている HTTP の版を確かめる ／ 達成=正しい版 ／ ヒント=①詳しく表示 ②版の欄 ③curl -I --http2 の結果 ／ エラー=違う→原因候補「ブラウザと curl の違い」
- 結果: 成功=版を確かめられた ／ 未達=表示の読み方を示す
- まとめ: ①HTTP/2 は並行 ②HTTP/3 は UDP の上 ③URL は変わらない ／ 次: web.a.01

### web.a.01 遅い Web を調べる（性能・上級）
- 解説: 何か=遅さの内訳（名前解決・接続・TLS・処理・転送）を分けて測ること ｜ なぜ=どこが遅いかで対策が全く違う ｜ 何に=性能の障害対応 ｜ 場面=ページの表示に 5 秒かかる
- 図: 1 回の依頼の時間を 5 つの区間に分けた横棒
- 理解: [図] 最も長い区間を押す ／ [状況説明] 区間ごとの対策を結ぶ

### web.a.02 4xx と 5xx を直す（障害・上級）
- 解説: 何か=返事の数字とログから、入口・アプリ・後ろのどこが原因かを特定して直す ｜ なぜ=Web の障害は利用者に直結する ｜ 何に=障害対応 ｜ 場面=一部の利用者だけ 500 になる
- 図: 入口の Web サーバ → アプリ → DB と、それぞれのログ
- 理解: [並べ替え] 見る順 ／ [状況説明] 502 と 504 の違い
- クイズ: [原因特定] 502 → 後ろに届かない ／ [原因特定] 504 → 後ろが遅すぎる ／ [状況判断] 500 → アプリのログ ／ [結果予測] 中継先のポートを直す → 502 が消え、アプリ側のエラーが見える
- 実戦（端）: 初期=中継先の誤りとアプリの設定の誤りが重なる ／ 目的=2 つ直して 200 に戻す ／ 達成=全ての依頼で 200 ／ ヒント=①入口のログ ②アプリのログ ③2 つの修正 ／ エラー=まだ 500→原因候補「アプリ側が残る」
- 結果: 成功=層をまたいで直せた ／ 未達=残っている原因の層を示す
- まとめ: ①数字で層を推測 ②各層のログ ③直したら全体で確かめる ／ 次: trouble.i.03

### web.a.03 認証付き API（API・上級）
- 解説: 何か=トークンを付けて呼ぶ API と、失敗した時の扱い ｜ なぜ=誰の依頼かを確かめ、許された操作だけ行うため ｜ 何に=外部サービスとの連携 ｜ 場面=API が 401 を返す
- 図: トークンを取得 → Authorization の見出しに付けて依頼 → 期限切れで 401 → 取り直し
- 理解: [関係性] 401 と 403 → 誰か分からない／権限が無い ／ [はい・いいえ] トークンをコードに直書きしてよい → いいえ
- クイズ: [原因特定] 401 → トークンが無いか期限切れ ／ [原因特定] 403 → 権限が足りない ／ [状況判断] トークンの置き場所 → 環境変数や秘密の保管場所 ／ [結果予測] 期限切れのトークンで呼ぶ → 401
- 実戦（端）: 目的=環境変数のトークンを使って API を呼び、期限切れの時に取り直す ／ 達成=2 回目の呼び出しも成功 ／ ヒント=①見出しに付ける ②401 の時の手順 ③完成したコマンド ／ エラー=401→原因候補「Bearer の綴り」「期限切れ」
- 結果: 成功=安全にトークンを使えた ／ 未達=見出しの違いを示す
- まとめ: ①トークンは見出しで送る ②401 と 403 の違い ③トークンを直書きしない ／ 次: sec.i.05
