### k8s.b.01 Kubernetes とは・なぜ必要か（考え方・初級）
- 解説: 何か=多数の機械の上で、コンテナを「決めた形のまま」動かし続ける仕組み ｜ なぜ=コンテナが数十・数百になると、人が手で配置し、落ちたら立て直すのは間に合わない ｜ 何に=止まらないサービス・規模の変化への対応 ｜ 場面=夜中にサーバが 1 台止まった
- 状況説明: 夜中にサーバが 1 台止まり、そこで動いていたアプリを人が手で別のサーバへ移す必要がある
- 図: 「3 つ動かす」と宣言 → Kubernetes が配置し、落ちたら作り直す
- 理解: [関係性] 宣言と実現 → あるべき形を伝えると、仕組みが合わせる ／ [状況説明] 手作業の限界を選ぶ
- クイズ: [用語] 宣言的 → あるべき形を伝える ／ [状況判断] 落ちたら自動で → Kubernetes ／ [結果予測] サーバが 1 台止まる → 他のサーバで作り直される
- 実戦（端）: 目的=3 台の Node に手で置いた Pod（web-1〜3）と、web を 3 つと宣言した Deployment で、node-2 を空けた（kubectl drain）時の web の数を比べる ／ 達成=①node-2 が空く ②残った web の数（2）を答える ③uncordon して Deployment を作り、もう一度 drain しても web が 3 つ Ready ／ ヒント=①get pods -o wide と drain ②持ち主の無い Pod には --force が要る ③kubectl drain node-2 --force、kubectl uncordon node-2、kubectl create deployment web --image=nginx --replicas=3、kubectl drain node-2 ／ エラー=cannot delete Pods that declare no controller→原因候補「手で置いた Pod で、持ち主がいない」
- 結果: 成功=必要性を体感 ／ 未達=比較の結果を示す
- まとめ: ①あるべき形を宣言する ②仕組みが合わせ続ける ③コンテナを束ねる仕組み ／ 次: k8s.b.02

### k8s.b.02 コンテナとの関係（関係・初級）
- 解説: 何か=コンテナを Pod に入れ、Pod を Node に置き、Node の集まりがクラスタ ｜ なぜ=この包含関係が分かれば、どこを見ればよいかが分かる ｜ 何に=全ての操作の土台 ｜ 場面=「Pod が動かない」と言われた
- 図: クラスタ ⊃ Node ⊃ Pod ⊃ コンテナ
- 理解: [図] 4 つを入れ子に並べる ／ [はい・いいえ] Pod には必ずコンテナが 1 つだけ → いいえ（複数入れられる）
- クイズ: [用語] Pod → コンテナを入れる最小の単位 ／ [選択] Node → コンテナを動かす機械 ／ [結果予測] Node が止まる → その上の Pod が止まる
- 実戦（端）: 目的=city-cluster の入れ子（クラスタ ⊃ Node ⊃ Pod ⊃ コンテナ）を外側から kubectl で読む ／ 達成=①Node の数（2） ②web の Pod の Node（node-1） ③Pod の中のログを集めるコンテナの名前（log-agent）を答える ／ ヒント=①kubectl get nodes ②kubectl get pods -o wide の NODE ③kubectl describe pod web の Containers ／ エラー=取り違え→原因候補「Pod や Node の名前を答えた」
- 結果: 成功=包含関係を理解 ／ 未達=図を示す
- まとめ: ①クラスタ・Node・Pod・コンテナ ②Pod が最小の単位 ③Node は機械 ／ 次: k8s.b.03

### k8s.b.03 クラスタと Node（クラスタ・初級）
- 解説: 何か=全体を管理する制御の側（コントロールプレーン）と、Pod を動かす Node ｜ なぜ=指示を受ける所と動かす所を分けている ｜ 何に=状態の確認 ｜ 場面=クラスタに何台の機械があるか確かめる
- 図: 制御の側（窓口・台帳・配置係・監督）と Node たち
- 理解: [図] 4 つの役割を制御の側に置く ／ [関係性] kubectl → 窓口に頼む
- クイズ: [選択] Node の一覧 → kubectl get nodes ／ [原因特定] NotReady → その Node が使えない ／ [用語] 配置係 → Pod を置く Node を決める
- 実戦（端）: 目的=Node の一覧から台数と状態を答える ／ 達成=正しい回答 ／ ヒント=①一覧 ②STATUS の欄 ③kubectl get nodes ／ エラー=接続できない→原因候補「接続先の設定」
- 結果: 成功=クラスタの形を確かめた ／ 未達=表の読み方を示す
- まとめ: ①制御の側と Node ②kubectl は窓口に頼む ③get nodes で状態 ／ 次: k8s.b.04, k8s.b.07

### k8s.b.04 Pod（Pod・初級）
- 解説: 何か=Kubernetes で動かす最小の単位 ｜ なぜ=全ての作業の出発点。状態の読み方を覚える ｜ 何に=アプリを動かす ｜ 場面=Pod が Pending のまま
- 図: Pending → ContainerCreating → Running の順と、それぞれの意味
- 理解: [並べ替え] 状態の順 ／ [状況説明] Pending の意味 → まだ置き場所が決まっていない
- クイズ: [結果予測] 作った直後 → Pending ／ [原因特定] Pending のまま → 置ける Node が無い ／ [選択] 詳しく見る → describe
- 実戦（端）: 目的=Pod を 1 つ作り、Running になるまで状態を追う ／ 達成=Running ／ ヒント=①作る ②状態を見る ③kubectl run web --image=nginx と get pods ／ エラー=ImagePullBackOff→原因候補「イメージの名前」
- 結果: 成功=状態を追えた ／ 未達=状態の遷移を示す
- まとめ: ①Pod が最小の単位 ②状態の順を知る ③詳しくは describe ／ 次: k8s.b.05

### k8s.b.05 Deployment（Deployment・初級）
- 解説: 何か=「この Pod をいつも 3 つ」と宣言すると、数を保ち続ける仕組み ｜ なぜ=手で面倒を見ると夜中の故障に間に合わない ｜ 何に=止まらないサービス・更新・拡縮 ｜ 場面=Pod が 1 つ消えた
- 図: あるべき数と現実の数を比べ、差を埋める。Deployment ⊃ ReplicaSet ⊃ Pod
- 理解: [関係性] 差を埋める動きを順に並べる ／ [図] 包含関係
- クイズ: [結果予測] Pod を 1 つ消す → 作り直される ／ [状況判断] 数を 5 に → scale ／ [用語] 宣言的 → あるべき形を伝える
- 実戦（端）: 目的=web を 3 つで動かし、1 つ消して戻ることを確かめる ／ 達成=Ready が 3 ／ ヒント=①作る ②消して待つ ③create deployment と delete pod と get pods ／ エラー=戻らない→原因候補「Deployment でなく単独の Pod を消した」
- 結果: 成功=数を保つ仕組みを確かめた ／ 未達=数の推移を示す
- まとめ: ①数を宣言すると保ち続ける ②消えても作り直す ③数は scale で変える ／ 次: k8s.b.06, k8s.i.06

### k8s.b.06 Service（Service・初級）
- 解説: 何か=入れ替わる Pod に、変わらない入口を与える仕組み ｜ なぜ=Pod は作り直されるたびに住所が変わる ｜ 何に=アプリどうしの通信・公開 ｜ 場面=Pod の住所を直接指していたら、作り直しでつながらなくなった
- 図: Service の入口 → 札（ラベル）の合う Ready な Pod にだけ振り分け
- 理解: [関係性] ラベルとセレクタ → 札で宛先を選ぶ ／ [はい・いいえ] Ready でない Pod にも送られる → いいえ
- クイズ: [結果予測] Pod が入れ替わる → Service の入口は同じ ／ [原因特定] 届かない → 札が合っていない ／ [選択] 宛先の一覧 → Endpoints
- 実戦（端）: 目的=web に Service を付け、Pod を作り直しても届くことを確かめる ／ 達成=作り直し後も応答 ／ ヒント=①付ける ②宛先の一覧 ③expose と get endpoints ／ エラー=宛先が空→原因候補「札の食い違い」
- 結果: 成功=変わらない入口を作れた ／ 未達=札の対応を示す
- まとめ: ①Service は変わらない入口 ②札で宛先を選ぶ ③宛先は Endpoints で確かめる ／ 次: k8s.i.04, k8s.a.03

### k8s.b.07 Namespace（Namespace・初級）
- 解説: 何か=クラスタの中を区画に分ける仕組み ｜ なぜ=チームや用途ごとに分け、名前の衝突と誤操作を防ぐ ｜ 何に=開発と本番の分離・チームの分離 ｜ 場面=他のチームの Pod を消してしまった
- 図: 1 つのクラスタの中の 3 つの区画
- 理解: [関係性] 区画と名前 → 区画が違えば同じ名前を使える ／ [はい・いいえ] -n を省くといつも全ての区画 → いいえ
- クイズ: [選択] 区画を指定 → -n ／ [原因特定] 見つからない → 区画が違う ／ [状況判断] 開発と本番 → 区画を分ける
- 実戦（端）: 目的=dev と prod の区画を作り、それぞれに web を置く ／ 達成=2 つの区画に同名の web ／ ヒント=①作る ②区画を指定 ③create namespace と -n ／ エラー=AlreadyExists→原因候補「区画の指定を忘れた」
- 結果: 成功=区画で分けた ／ 未達=どの区画に作ったかを示す
- まとめ: ①区画で分ける ②名前は区画ごと ③-n で指定 ／ 次: k8s.i.01

### k8s.i.01 ConfigMap（設定・中級）
- 解説: 何か=設定の値をイメージから切り離して渡す仕組み ｜ なぜ=設定を変えるたびにイメージを作り直さない ｜ 何に=接続先・機能の切り替え ｜ 場面=本番と検証で接続先だけ違う
- 図: ConfigMap → 環境変数かファイルとして Pod へ
- 理解: [関係性] 設定とイメージの分離 ／ [はい・いいえ] ConfigMap に秘密を入れてよい → いいえ
- クイズ: [状況判断] 接続先の切り替え → ConfigMap ／ [結果予測] 値を変える → 環境変数は Pod を作り直すまで変わらない ／ [選択] 渡し方 → 環境変数かファイル
- 実戦（編）: 目的=接続先を ConfigMap で渡し、値を変えて反映させる ／ 達成=新しい値で動く ／ ヒント=①作る ②渡す ③作り直して反映 ／ エラー=古い値→原因候補「Pod を作り直していない」
- 結果: 成功=設定を切り離せた ／ 未達=反映の仕組みを示す
- まとめ: ①設定はイメージと分ける ②環境変数かファイルで渡す ③反映の仕方に注意 ／ 次: k8s.i.02

### k8s.i.02 Secret（秘密・中級）
- 解説: 何か=秘密の値を渡すための仕組みと、その限界 ｜ なぜ=設定と秘密を分け、扱う人を絞る ｜ 何に=DB のパスワード・API の鍵 ｜ 場面=DB のパスワードを YAML に直書きしていた
- 図: Secret → Pod。保存は符号化されているだけで、権限の管理が要る
- 理解: [はい・いいえ] Secret は暗号化されているので誰が見てもよい → いいえ ／ [関係性] 権限で見られる人を絞る
- クイズ: [状況判断] パスワード → Secret ／ [原因特定] リポジトリに値がある → YAML に直書き ／ [結果予測] base64 → 元に戻せる
- 実戦（編）: 目的=直書きのパスワードを Secret に移し、Pod に渡す ／ 達成=YAML に値が無く、動く ／ ヒント=①作る ②参照 ③完成した YAML ／ エラー=値が空→原因候補「キーの名前の誤り」
- 結果: 成功=秘密を分けた ／ 未達=参照の誤りを示す
- まとめ: ①秘密は Secret に ②符号化は暗号ではない ③見られる人を絞る ／ 次: sec.i.05

### k8s.i.03 Volume（PV と PVC）（保存・中級）
- 解説: 何か=データを残す領域（PV）と、それを求める申請（PVC） ｜ なぜ=Pod は作り直される。データを外に置く ｜ 何に=DB・アップロード ｜ 場面=DB の Pod を作り直したらデータが消えた
- 図: Pod → PVC（申請）→ PV（実際の領域）
- 理解: [並べ替え] 申請から利用まで ／ [関係性] PV と PVC
- クイズ: [結果予測] PVC を付けて作り直す → データが残る ／ [原因特定] Pending → 合う領域が無い ／ [選択] 申請に書く物 → 大きさと使い方
- 実戦（編）: 目的=DB に PVC を付け、作り直してもデータが残ることを確かめる ／ 達成=残る ／ ヒント=①申請 ②付ける ③完成した YAML ／ エラー=Pending→原因候補「大きさや種類の食い違い」
- 結果: 成功=データを残せた ／ 未達=申請と領域の対応を示す
- まとめ: ①PVC で申請 ②PV が実体 ③付けて作り直しで確かめる ／ 次: k8s.a.01

### k8s.i.04 Ingress（公開・中級）
- 解説: 何か=名前やパスで振り分けて、外に公開する入口 ｜ なぜ=Service ごとに外の扉を作らず、入口を 1 つにまとめる ｜ 何に=複数のアプリの公開・HTTPS ｜ 場面=shop と api を同じ入口から出したい
- 図: Ingress → 名前・パスの規則 → Service → Pod
- 理解: [図] 規則に合う宛先を選ぶ ／ [関係性] Ingress と Service
- クイズ: [原因特定] 404 → 規則に合う物が無い ／ [原因特定] 503 → 後ろの Service に Pod が無い ／ [状況判断] HTTPS → Ingress に証明書 ／ [結果予測] 規則に /api を足す → /api の依頼が後ろの Service に届く
- 実戦（編）: 目的=shop と api を 1 つの Ingress で振り分ける ／ 達成=両方とも 200 ／ ヒント=①規則 ②宛先の Service ③完成した YAML ／ エラー=404→原因候補「名前の綴り」
- 結果: 成功=入口をまとめた ／ 未達=当たった規則を示す
- まとめ: ①Ingress は入口 ②名前とパスで振り分け ③後ろは Service ／ 次: k8s.a.01, k8s.a.03

### k8s.i.05 ヘルスチェック（健全性・中級）
- 解説: 何か=生きているか（liveness）と、受け付けてよいか（readiness）の確認 ｜ なぜ=固まった物を作り直し、準備中の物に送らない ｜ 何に=止まらないサービス ｜ 場面=起動直後にエラーが返る
- 図: readiness が通るまで宛先に入らない。liveness に失敗すると作り直し
- 理解: [関係性] 2 つの確認の違い ／ [状況説明] 起動直後のエラーの原因
- クイズ: [状況判断] 準備中に送らない → readiness ／ [状況判断] 固まったら作り直す → liveness ／ [原因特定] 何度も作り直される → liveness が厳しすぎる ／ [結果予測] readiness が通らない Pod → Service の宛先に入らない
- 実戦（編）: 目的=起動に 20 秒かかるアプリに、2 つの確認を正しく付ける ／ 達成=起動中は送られず、固まると作り直される ／ ヒント=①確認の URL ②待つ時間 ③完成した YAML ／ エラー=作り直しが続く→原因候補「待つ時間が短い」
- 結果: 成功=確認を設計 ／ 未達=確認の結果の推移を示す
- まとめ: ①readiness は送ってよいか ②liveness は生きているか ③待つ時間を合わせる ／ 次: mon.b.04

### k8s.i.06 スケーリング（規模・中級）
- 解説: 何か=Pod の数を手で、または負荷に応じて自動で変える ｜ なぜ=混む時だけ増やし、空いたら減らす ｜ 何に=負荷の変化への対応 ｜ 場面=昼だけ利用者が 10 倍になる
- 図: CPU の使用率に応じて数が増減する
- 理解: [関係性] 自動の拡縮と目標の値 ／ [はい・いいえ] 自動の拡縮は資源の要求の設定が無くても動く → いいえ
- クイズ: [選択] 手で → scale ／ [状況判断] 負荷に応じて → 自動の拡縮 ／ [原因特定] 増えない → 要求の設定が無い
- 実戦（端）: 目的=CPU 50% を目標に 2〜10 の範囲で自動で増減させる ／ 達成=負荷の模擬で増え、止めると減る ／ ヒント=①要求 ②範囲と目標 ③autoscale のコマンド ／ エラー=増えない→原因候補「要求が無い」
- 結果: 成功=自動の拡縮を設定 ／ 未達=数の推移を示す
- まとめ: ①手でも自動でも ②目標と範囲 ③要求の設定が要る ／ 次: k8s.i.07, cloud.i.02

### k8s.i.07 資源の要求と上限（資源・中級）
- 解説: 何か=最低限ほしい量（requests）と、使ってよい上限（limits） ｜ なぜ=置き場所の判断と、取り合いの防止 ｜ 何に=安定した運用 ｜ 場面=Pod が Pending のまま、または強制終了される
- 図: Node の容量と、各 Pod の要求の積み上げ
- 理解: [関係性] 要求は配置に、上限は実行に効く ／ [状況説明] Pending と強制終了の違い
- クイズ: [原因特定] Pending → 要求に合う空きが無い ／ [原因特定] OOMKilled → メモリの上限を超えた ／ [状況判断] 要求を大きくしすぎる → 置けなくなる ／ [用語] requests → 配置の時に確保を求める量
- 実戦（編）: 目的=Pending の Pod と、強制終了される Pod の値を直す ／ 達成=両方動き続ける ／ ヒント=①空きと要求 ②使用量と上限 ③値 ／ エラー=まだ止まる→原因候補「上限が実際の使用量より低い」
- 結果: 成功=値を合わせた ／ 未達=容量の図を示す
- まとめ: ①要求は配置 ②上限は実行 ③実際の使用量から決める ／ 次: k8s.a.02

### k8s.i.08 ローリングアップデート（更新・中級）
- 解説: 何か=Pod を少しずつ入れ替えて、止めずに新しい版にする ｜ なぜ=利用者を止めずに更新し、失敗したら戻す ｜ 何に=本番の更新 ｜ 場面=新しい版を配りたいが止められない
- 図: 古い Pod が 1 つずつ新しい Pod に入れ替わる
- 理解: [並べ替え] 入れ替わりの順 ／ [関係性] readiness と更新 → 準備ができた物から入れ替える
- クイズ: [選択] 進み具合 → rollout status ／ [状況判断] 失敗した → rollout undo ／ [結果予測] 新しい版が起動しない → 古い版が残り続ける
