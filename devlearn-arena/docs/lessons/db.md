# レッスン設計: データベース（db）— データセンター

書式は `docs/lessons/README.md`。実戦はブラウザ内の SQLite で本物の SQL を実行する。

### db.b.01 データベースとは（考え方・初級）
- 解説: 何か=大量のデータを、整理し、速く・正しく出し入れするための仕組み ｜ なぜ=ファイルでは同時の書き込み・検索・整合性が保てない ｜ 何に=会員・注文・在庫 ｜ 場面=表計算のファイルを 2 人が同時に直して食い違った
- 図: ファイルで管理した場合と DB で管理した場合の比較
- 理解: [状況説明] ファイルで困る場面を選ぶ ／ [用語] DB・DBMS・SQL を結ぶ
- クイズ: [選択] DB を使う理由 → 同時の出し入れと整合性 ／ [用語] SQL → DB に頼む言葉 ／ [状況判断] 注文と在庫を同時に更新 → DB
- 実戦（模）: 目的=ファイルで起きた食い違いを DB に移して防ぐ ／ 達成=同時の更新でも食い違わない ／ ヒント=①何が食い違うか ②同時の更新 ③DB に移す ／ エラー=まだ食い違う→原因候補「ファイルにも書いている」
- 結果: 成功=DB の価値を体感 ／ 未達=食い違いの経過を示す
- まとめ: ①DB は整理と整合性 ②SQL で頼む ③同時の出し入れに強い ／ 次: db.b.02

### db.b.02 テーブル・行・列（テーブル・初級）
- 解説: 何か=データを表の形（テーブル）で持ち、1 件が行、項目が列 ｜ なぜ=形を決めると、探す・並べる・数えるが簡単になる ｜ 何に=全ての RDB ｜ 場面=会員の一覧を作る
- 図: members テーブルの行と列と、主キー
- 理解: [図] 行と列を押す ／ [用語] 主キー → 行を 1 つに決める列
- クイズ: [選択] 1 件のデータ → 行 ／ [状況判断] 会員を区別する列 → id（主キー） ／ [原因特定] 同じ id が 2 つ → 主キーが無い
- 実戦（S）: 目的=members テーブルを作り、3 件入れる ／ 達成=3 件ある ／ ヒント=①列の定義 ②入れる ③CREATE TABLE と INSERT ／ エラー=型の誤り→原因候補「列の型と値が合わない」
- 結果: 成功=表を作れた ／ 未達=表の中身を示す
- まとめ: ①テーブル・行・列 ②主キーで区別 ③列ごとに型 ／ 次: db.b.03

### db.b.03 SELECT（SQL・初級）
- 解説: 何か=必要な列と行を取り出す命令 ｜ なぜ=DB で一番多く使う操作 ｜ 何に=一覧・検索 ｜ 場面=東京の会員の名前だけほしい
- 図: SELECT 列 FROM 表 WHERE 条件 の形
- 理解: [図] 3 つの部分を押す ／ [並べ替え] 書く順
- クイズ: [結果予測] SELECT name FROM members → 名前の列だけ ／ [選択] 全ての列 → * ／ [原因特定] no such column → 列名の誤り
- 実戦（S）: 目的=東京の会員の名前を取り出す ／ 達成=正しい結果 ／ ヒント=①列 ②条件 ③SELECT name FROM members WHERE city='東京' ／ エラー=0 件→原因候補「値の綴り」
- 結果: 成功=取り出せた ／ 未達=条件の違いを示す
- まとめ: ①SELECT で取り出す ②WHERE で絞る ③列名は正確に ／ 次: db.b.04, sec.i.03

### db.b.04 絞り込み・並べ替え・集計（SQL・初級）
- 解説: 何か=WHERE で絞り、ORDER BY で並べ、GROUP BY で数える ｜ なぜ=報告や判断に要る形にする ｜ 何に=売上の集計 ｜ 場面=地域ごとの会員数を多い順に
- 図: 絞る → まとめる → 並べる の流れ
- 理解: [並べ替え] 処理の順 ／ [用語] COUNT・SUM・AVG を結ぶ
- クイズ: [結果予測] GROUP BY city → 地域ごとに 1 行 ／ [選択] 多い順 → DESC ／ [原因特定] 集計が合わない → 絞り込みの漏れ
- 実戦（S）: 目的=地域ごとの会員数を多い順に出す ／ 達成=正しい結果 ／ ヒント=①まとめる列 ②数える ③完成した SQL ／ エラー=列が集計されていない→原因候補「GROUP BY に無い列を選んだ」
- 結果: 成功=集計できた ／ 未達=途中の結果を示す
- まとめ: ①WHERE で絞る ②GROUP BY で数える ③ORDER BY で並べる ／ 次: db.i.01, db.i.03

### db.b.05 追加・更新・削除（SQL・初級）
- 解説: 何か=INSERT・UPDATE・DELETE ｜ なぜ=データを変える。誤ると全件が変わる ｜ 何に=登録・変更・退会 ｜ 場面=1 人の住所を変えるつもりが全員変わった
- 図: WHERE の有無で変わる範囲の違い
- 理解: [はい・いいえ] WHERE の無い UPDATE は 1 件だけ変わる → いいえ ／ [状況説明] 安全な手順を選ぶ
- クイズ: [結果予測] UPDATE members SET city='大阪' → 全員が大阪 ／ [状況判断] 変える前に → 同じ条件で SELECT ／ [原因特定] 全員消えた → WHERE が無い
- 実戦（S）: 目的=id 3 の会員の住所を変え、id 5 を消す ／ 達成=その 2 件だけが変わる ／ ヒント=①条件 ②先に SELECT で確かめる ③2 つの SQL ／ エラー=多く変わった→原因候補「条件の誤り」
- 結果: 成功=安全に変えた ／ 未達=変わった範囲を示す
- まとめ: ①変える前に SELECT ②WHERE を忘れない ③範囲を確かめる ／ 次: db.i.04

### db.i.01 JOIN（結合・中級）
- 解説: 何か=複数の表を、共通の列で結び付けて取り出す ｜ なぜ=データを重複させずに分けて持ち、必要な時に結ぶ ｜ 何に=注文と会員の結合 ｜ 場面=注文の一覧に会員の名前を付けたい
- 図: orders.member_id と members.id で結ぶ
- 理解: [関係性] 結ぶ列 ／ [状況説明] INNER と LEFT の違い
- クイズ: [結果予測] INNER JOIN → 両方にある物だけ ／ [状況判断] 注文が無い会員も → LEFT JOIN ／ [原因特定] 行が増えすぎる → 結ぶ条件の誤り
- 実戦（S）: 目的=注文の一覧に会員の名前を付ける ／ 達成=正しい結果 ／ ヒント=①結ぶ列 ②JOIN ③完成した SQL ／ エラー=ambiguous column→原因候補「同名の列に表名を付けていない」
- 結果: 成功=表を結べた ／ 未達=結ぶ列を示す
- まとめ: ①共通の列で結ぶ ②INNER と LEFT ③同名の列には表名 ／ 次: db.i.02

### db.i.02 RDB の設計（設計・中級）
- 解説: 何か=重複を減らすように表を分ける考え方（正規化） ｜ なぜ=同じ情報が何か所にもあると、直し漏れで食い違う ｜ 何に=新しい仕組みの設計 ｜ 場面=会員の住所を直したのに、注文の表は古いまま
- 図: 1 つの大きな表と、会員・注文に分けた表
- 理解: [状況説明] 重複で起きる問題 ／ [関係性] 分けた表と JOIN
- クイズ: [原因特定] 直し漏れ → 同じ情報の重複 ／ [状況判断] 会員の情報 → 会員の表だけに持つ ／ [選択] 表どうしをつなぐ列 → 外部キー
- 実戦（S）: 目的=重複のある表を 2 つに分け、結合で元の一覧を作る ／ 達成=重複が無く同じ一覧が出る ／ ヒント=①重複している列 ②分ける ③CREATE と INSERT と SELECT ／ エラー=一覧が合わない→原因候補「結ぶ列の値の誤り」
- 結果: 成功=重複を減らした ／ 未達=重複の箇所を示す
- まとめ: ①情報は 1 か所に ②表を分けて結ぶ ③外部キーでつなぐ ／ 次: db.i.05

### db.i.03 インデックス（性能・中級）
- 解説: 何か=検索を速くする索引 ｜ なぜ=全ての行を順に見ると、件数が増えると遅くなる ｜ 何に=よく使う検索条件 ｜ 場面=会員が 100 万人になり検索が遅い
- 図: 索引の無い全件の走査と、索引を使った検索
- 理解: [関係性] 索引と書き込みの速さ → 書き込みは少し遅くなる ／ [状況説明] 索引を付ける列を選ぶ
- クイズ: [状況判断] よく WHERE に使う列 → 索引 ／ [結果予測] 索引の後の検索 → 速くなる ／ [原因特定] まだ遅い → 条件の列と索引の列が違う
- 実戦（S）: 目的=遅い検索の実行計画を見て、索引を付けて速くする ／ 達成=計画が索引を使う ／ ヒント=①計画を見る ②条件の列 ③CREATE INDEX ／ エラー=使われない→原因候補「列の違い」
- 結果: 成功=速くできた ／ 未達=計画の違いを示す
- まとめ: ①索引で検索が速く ②書き込みは少し遅く ③よく使う条件に付ける ／ 次: db.a.02

### db.i.04 トランザクション（整合・中級）
- 解説: 何か=複数の更新をひとまとまりにし、全部成功か全部無しにする仕組み ｜ なぜ=振込で片方だけ減ると困る ｜ 何に=お金・在庫・予約 ｜ 場面=途中で落ちたら残高が合わない
- 図: BEGIN → 更新 2 つ → COMMIT。途中で失敗すれば ROLLBACK
- 理解: [並べ替え] 流れの順 ／ [用語] 原子性 → 全部か無し
- クイズ: [結果予測] ROLLBACK 後 → 元の残高 ／ [状況判断] 在庫を減らし注文を作る → 1 つのトランザクション ／ [原因特定] 反映されない → COMMIT していない
- 実戦（S）: 目的=A から B へ 1,000 円を移す。途中の失敗でも合計が変わらない ／ 達成=合計が一定 ／ ヒント=①2 つの UPDATE ②囲む ③BEGIN … COMMIT ／ エラー=片方だけ→原因候補「囲んでいない」
- 結果: 成功=整合を保てた ／ 未達=途中の状態を示す
- まとめ: ①全部か無し ②BEGIN と COMMIT ③失敗は ROLLBACK ／ 次: db.a.01

### db.i.05 NoSQL の基本概念（種類・中級）
- 解説: 何か=表の形にこだわらない DB（文書型・キーバリュー型など） ｜ なぜ=形の変わりやすいデータや、大量の単純な読み書きに向く ｜ 何に=設定・ログ・キャッシュ ｜ 場面=商品ごとに項目が違う
- 図: 表の形と、文書の形・キーと値の形の比較
- 理解: [関係性] 向き不向き ／ [はい・いいえ] NoSQL は RDB より常に優れる → いいえ
- クイズ: [状況判断] 項目が商品ごとに違う → 文書型 ／ [状況判断] 速い読み出しの一時保存 → キーバリュー型 ／ [選択] お金の正確さが要る → RDB ／ [結果予測] 文書型に項目の違う商品を入れる → 表を作り直さずに入る
- 実戦（模）: 目的=4 つの用途に合う種類を選ぶ ／ 達成=理由付きで正しい ／ ヒント=①形の変わりやすさ ②整合性 ③答え ／ エラー=取り違え→原因候補「流行で選んだ」
- 結果: 成功=使い分けられた ／ 未達=比較表を示す
- まとめ: ①表以外の形もある ②用途で選ぶ ③整合性が要るなら RDB ／ 次: cloud.b.02

### db.a.01 バックアップと復元（保全・上級）
- 解説: 何か=データの控えを取り、壊れた時に戻す ｜ なぜ=誤った削除や故障は必ず起きる ｜ 何に=運用 ｜ 場面=誤って全件を消した
- 図: 定期の控え → 保管 → 復元の練習
- 理解: [並べ替え] 取る → 保管 → 試しに戻す ／ [はい・いいえ] 控えを取るだけで安心 → いいえ（戻せることを確かめる）
- クイズ: [状況判断] 控えの置き場所 → 別の場所 ／ [原因特定] 戻せない → 試したことが無い ／ [結果予測] 1 日 1 回の控え → 最大 1 日分を失う
- 実戦（S）: 目的=控えを取り、誤って消した後に戻す ／ 達成=元の件数に戻る ／ ヒント=①控え ②消える ③戻す手順 ／ エラー=古い状態→原因候補「古い控えを使った」
- 結果: 成功=戻せた ／ 未達=どの控えを使ったかを示す
- まとめ: ①控えは別の場所 ②戻せることを確かめる ③失う量を決めて頻度を決める ／ 次: db.a.03

### db.a.02 DB の障害対応（障害・上級）
- 解説: 何か=ロック待ち・遅いクエリ・容量不足を切り分けて直す ｜ なぜ=DB が止まると全てが止まる ｜ 何に=障害対応 ｜ 場面=注文の画面が固まる
- 図: 症状 → 実行中の処理の一覧・遅い記録・容量 → 原因
- 理解: [並べ替え] 調べる順 ／ [状況説明] ロック待ちの連鎖
- クイズ: [原因特定] 1 つの更新が終わらず他が待つ → ロック ／ [原因特定] 特定の画面だけ遅い → 遅いクエリ ／ [状況判断] 容量が尽きそう → 古いデータの整理 ／ [結果予測] 終わらない更新を止める → 待っていた処理が進む
- 実戦（S）: 初期=終わらない更新が他を止めている ／ 目的=原因の処理を特定して止め、遅いクエリに索引を付ける ／ 達成=画面が応答 ／ ヒント=①実行中の処理 ②止める・索引 ③手順 ／ エラー=まだ遅い→原因候補「索引の列」
- 結果: 成功=DB の障害を切り分けた ／ 未達=待ちの連鎖を示す
- まとめ: ①実行中の処理を見る ②遅い記録を見る ③容量も確かめる ／ 次: trouble.a.02

### db.a.03 レプリケーションの考え方（冗長・上級）
- 解説: 何か=DB の写しを別の機械に作り続ける仕組み ｜ なぜ=1 台が壊れても続け、読み出しを分ける ｜ 何に=止まらない DB ｜ 場面=写しから読んだら少し古いデータが出た
- 図: 書く側 → 写し（少し遅れる）→ 読む側
- 理解: [関係性] 写しの遅れ ／ [状況説明] 古いデータが出る理由
- クイズ: [結果予測] 書いた直後に写しを読む → 古いことがある ／ [状況判断] 書いた直後の確認 → 書く側から読む ／ [選択] 目的 → 故障への備えと読み出しの分散
- 実戦（模）: 目的=写しの遅れで起きる表示の食い違いを、読む先を変えて防ぐ ／ 達成=食い違わない ／ ヒント=①遅れ ②読む先 ③設定 ／ エラー=まだ食い違う→原因候補「全ての読みを写しにした」
- 結果: 成功=遅れを考えて設計 ／ 未達=遅れの図を示す
- まとめ: ①写しで備える ②写しは少し遅れる ③直後の読みは書く側 ／ 次: cloud.i.01
