# レッスン設計: Git（git）— 開発オフィス

書式は `docs/lessons/README.md`。

### git.b.01 バージョン管理とは（考え方・初級）
- 解説: 何か=変更の履歴を残し、いつでも戻れるようにする仕組み ｜ なぜ=上書きで前の版が消える・誰が何を変えたか分からない ｜ 何に=コード・設定・文書 ｜ 場面=「昨日の版に戻して」と言われる
- 図: 上書きで消える版と、履歴として並ぶ版の比較
- 理解: [状況説明] 履歴が無いと困る場面を選ぶ ／ [用語] リポジトリ・コミットと説明を結ぶ
- クイズ: [選択] 管理する理由 → 戻れる・誰が何を変えたか分かる ／ [状況判断] 設定の変更も → 管理するとよい ／ [用語] コミット → 変更の記録 1 つ
- 実戦（模）: 目的=3 回書き直した設計図から、依頼主の言う版に戻す ／ 達成=指定の版に戻る ／ ヒント=①履歴の一覧 ②日付と説明 ③該当の版を選ぶ ／ エラー=違う版→原因候補「説明を読まずに選んだ」
- 結果: 成功=履歴の価値を体感 ／ 未達=履歴と目的の版を並べる
- まとめ: ①履歴を残す ②いつでも戻れる ③誰が何を変えたか分かる ／ 次: git.b.02

### git.b.02 最初の記録（commit・初級）
- 解説: 何か=init・status・add・commit で変更を記録する ｜ なぜ=記録する物を選び、意味のある単位で残す ｜ 何に=全ての変更管理 ｜ 場面=作り始めたプロジェクトを記録したい
- 図: 作業ツリー → add → インデックス → commit → 履歴
- 理解: [並べ替え] add と commit の順 ／ [関係性] インデックスの役割 → 次の記録に入れる物を選ぶ台
- クイズ: [結果予測] add せずに commit → 何も記録されない ／ [状況判断] 今の状態を見る → status ／ [用語] コミットの説明 → 何をなぜ変えたか
- 実戦（端）: 目的=リポジトリを作り、README を記録する ／ 達成=1 件のコミットがある ／ ヒント=①始める ②選ぶ ③git init; git add README.md; git commit -m "..." ／ エラー=nothing to commit→原因候補「add していない」
- 結果: 成功=最初の記録ができた ／ 未達=status の表示を示す
- まとめ: ①add で選び commit で記録 ②status で今を見る ③説明は分かりやすく ／ 次: git.b.03, git.b.04

### git.b.03 差分と履歴を見る（履歴・初級）
- 解説: 何か=diff で何が変わったか、log でいつ誰が変えたかを見る ｜ なぜ=記録する前に確かめ、後から原因を探す ｜ 何に=レビュー・障害の調査 ｜ 場面=昨日から動かない。何が変わったか
- 図: + と - で示した差分と、一覧の履歴
- 理解: [図] 差分の + と - を読む ／ [用語] log の各欄を結ぶ
- クイズ: [結果予測] git diff → まだ add していない変更 ／ [状況判断] 記録前に確かめる → diff --staged ／ [選択] 1 行ずつの履歴 → log --oneline
- 実戦（端）: 目的=昨日以降の変更から、設定の値を変えたコミットを特定する ／ 達成=正しいコミット ／ ヒント=①履歴 ②変更の中身 ③log と show ／ エラー=違う→原因候補「説明だけで判断した」
- 結果: 成功=変更を特定できた ／ 未達=差分を並べる
- まとめ: ①diff で何が ②log でいつ誰が ③記録前に確かめる ／ 次: git.i.04, git.a.01

### git.b.04 枝を分ける（branch・初級）
- 解説: 何か=作業の流れを分ける枝（ブランチ） ｜ なぜ=本番の版を壊さずに試せる・複数の作業を並べられる ｜ 何に=機能の追加・修正 ｜ 場面=新しい機能を試しながら、緊急の修正もしたい
- 図: main から feature が分かれる
- 理解: [関係性] 枝と履歴 ／ [はい・いいえ] 枝を作ると全てのファイルが複製される → いいえ
- クイズ: [選択] 枝を作って移る → switch -c ／ [状況判断] 試す作業 → 新しい枝で ／ [結果予測] 枝で記録 → main は変わらない
- 実戦（端）: 目的=feature 枝を作って変更を記録し、main が変わらないことを確かめる ／ 達成=feature に 1 件、main は変化なし ／ ヒント=①作って移る ②記録 ③git switch -c feature の後 commit ／ エラー=main に記録した→原因候補「枝を移っていない」
- 結果: 成功=作業を分けられた ／ 未達=どの枝にいたかを示す
- まとめ: ①枝で作業を分ける ②本番を壊さない ③今どの枝かを確かめる ／ 次: git.b.05

### git.b.05 枝を合わせる（merge・初級）
- 解説: 何か=枝の変更を別の枝に取り込む ｜ なぜ=試した作業を本番の流れに戻す ｜ 何に=機能の完成 ｜ 場面=feature の作業が終わった
- 図: feature を main に合わせる 2 つの形（そのまま進める・合わせる記録を作る）
- 理解: [関係性] どちらの枝にいて何を取り込むか ／ [状況説明] 合わせる記録ができる場合
- クイズ: [結果予測] main で merge feature → feature の変更が main に入る ／ [状況判断] 合わせる前に → main を最新に ／ [用語] fast-forward → 枝の先へ進めるだけ
- 実戦（端）: 目的=feature を main に合わせる ／ 達成=main に feature の変更がある ／ ヒント=①main に移る ②取り込む ③git switch main; git merge feature ／ エラー=逆に取り込んだ→原因候補「feature で merge main」
- 結果: 成功=作業を戻せた ／ 未達=枝の図を示す
- まとめ: ①取り込む側の枝に移る ②merge で取り込む ③合わせた後に確かめる ／ 次: git.b.06

### git.b.06 衝突を解く（conflict・初級）
- 解説: 何か=2 つの枝が同じ所を違うように変えた時の衝突 ｜ なぜ=自動ではどちらが正しいか決められない ｜ 何に=共同作業 ｜ 場面=merge したら止まった
- 図: <<<<<<< ======= >>>>>>> の各部分の意味
- 理解: [用語] 印の各部分を結ぶ ／ [図] どちらの変更かを示す
- クイズ: [結果予測] 両方が同じ行を変える → 衝突 ／ [状況判断] 衝突後の最初 → status ／ [用語] HEAD → 今いる枝
- 実戦（端）: 目的=料金表の衝突を、両方の意図を活かして解く ／ 達成=印が消え、正しい内容で記録 ／ ヒント=①衝突したファイル ②印の中を読む ③正しい形に直して add と commit ／ エラー=印が残った→原因候補「印ごと消していない」
- 結果: 成功=衝突を解けた ／ 未達=残った印を示す
- まとめ: ①衝突は人が決める合図 ②印を消して正しい形に ③add と commit で完了 ／ 次: git.i.01

### git.i.01 リモートと複製（remote・中級）
- 解説: 何か=手元とは別の場所にあるリポジトリ（リモート）と、その複製（clone） ｜ なぜ=共有し、手元の故障に備える ｜ 何に=チームでの開発・控え ｜ 場面=新しく参加したプロジェクトを手元に持ってくる
- 図: リモートと手元の 2 つのリポジトリ
- 理解: [関係性] origin とは → 既定のリモートの名前 ／ [はい・いいえ] clone すると履歴も来る → はい
- クイズ: [選択] 複製 → clone ／ [状況判断] リモートの一覧 → remote -v ／ [結果予測] clone の後の枝 → 既定の枝
- 実戦（端）: 目的=プロジェクトを複製し、リモートの名前と場所を答える ／ 達成=複製があり、正しく回答 ／ ヒント=①複製 ②リモートの一覧 ③git clone と git remote -v ／ エラー=認証の失敗→原因候補「鍵の登録」
- 結果: 成功=リモートを扱えた ／ 未達=手元とリモートの図を示す
- まとめ: ①リモートは別の場所の履歴 ②clone で丸ごと複製 ③既定の名前は origin ／ 次: git.i.02

### git.i.02 push と pull（同期・中級）
- 解説: 何か=手元の記録を送る push と、リモートの記録を取り込む pull（fetch と merge） ｜ なぜ=チームで同じ履歴を共有する ｜ 何に=共同作業 ｜ 場面=push が拒否された
- 図: 手元 → push → リモート、リモート → fetch → 手元 → merge
- 理解: [関係性] fetch と pull の違い ／ [状況説明] 拒否される理由
- クイズ: [原因特定] push が拒否 → リモートに手元に無い記録がある ／ [状況判断] まず取り込む → pull ／ [選択] 見るだけ → fetch
- 実戦（端）: 目的=拒否された push を、取り込んでから送り直す ／ 達成=リモートに自分の記録がある ／ ヒント=①取り込む ②衝突があれば解く ③pull の後 push ／ エラー=衝突→原因候補「同じ行の変更」
- 結果: 成功=履歴を同期できた ／ 未達=両方の履歴を並べる
- まとめ: ①push で送る ②pull で取り込む ③拒否されたら先に取り込む ／ 次: git.i.03

### git.i.03 GitHub / GitLab とプルリクエスト（共同作業・中級）
- 解説: 何か=変更を取り込む前に見てもらう依頼（プルリクエスト・マージリクエスト） ｜ なぜ=誤りを本番に入れる前に見つけ、知識を共有する ｜ 何に=チーム開発 ｜ 場面=自分の変更を main に入れたい
- 図: 枝 → 依頼 → レビューと自動の検査 → 取り込み
- 理解: [並べ替え] 依頼の流れ ／ [関係性] プルリクエストとマージリクエスト → 同じ考え方の別名
- クイズ: [状況判断] 取り込む前に → レビューと検査 ／ [原因特定] 取り込めない → 検査の失敗か承認の不足 ／ [選択] 依頼に書く事 → 何を・なぜ・どう確かめたか
- 実戦（模）: 目的=依頼を作り、指摘を直して承認を得て取り込む ／ 達成=取り込まれる ／ ヒント=①依頼を作る ②指摘への対応 ③直して再依頼 ／ エラー=取り込めない→原因候補「検査が失敗」
- 結果: 成功=レビューの流れを通せた ／ 未達=止まった段を示す
- まとめ: ①取り込む前に見てもらう ②検査と承認 ③説明を書く ／ 次: cicd.b.01, git.a.02

### git.i.04 変更を取り消す（取り消し・中級）
- 解説: 何か=restore（記録前の変更を戻す）・revert（打ち消す記録を作る）・reset（枝の先を動かす） ｜ なぜ=場面ごとに安全な戻し方が違う ｜ 何に=誤りの修正 ｜ 場面=共有した記録に誤りがあった
- 図: 3 つの取り消しの前後の履歴
- 理解: [関係性] 共有済みの記録には → revert ／ [状況説明] reset が危ない場面
- クイズ: [状況判断] 記録前の誤った編集 → restore ／ [状況判断] 共有済みの誤り → revert ／ [結果予測] reset --hard → 記録前の変更も消える ／ [用語] revert → 打ち消す記録を作る
- 実戦（端）: 目的=共有済みの誤った記録を、履歴を壊さずに打ち消す ／ 達成=打ち消す記録があり、内容が戻る ／ ヒント=①共有済みか ②打ち消す記録 ③git revert <ID> ／ エラー=他の人の履歴と食い違う→原因候補「reset した」
- 結果: 成功=安全に戻せた ／ 未達=履歴の変化を示す
- まとめ: ①記録前は restore ②共有済みは revert ③reset は手元だけで ／ 次: git.a.01, git.a.03

### git.i.05 rebase の考え方（履歴・中級）
- 解説: 何か=枝の付け根を付け替えて、履歴を一直線にする操作 ｜ なぜ=履歴を読みやすくする ｜ 何に=取り込む前の整理 ｜ 場面=main が進んでいて、自分の枝が古い
- 図: merge（合流の記録）と rebase（付け替え）の比較
- 理解: [関係性] merge と rebase の違い ／ [はい・いいえ] 共有した枝を rebase してよい → いいえ
- クイズ: [結果予測] rebase の後 → 記録の ID が変わる ／ [状況判断] 自分だけの枝を最新に → rebase してよい ／ [原因特定] 他の人と履歴が食い違う → 共有した枝を rebase した
- 実戦（端）: 目的=自分の枝を最新の main の上に付け替える ／ 達成=一直線の履歴 ／ ヒント=①自分の枝で ②付け替え先 ③git rebase main ／ エラー=衝突→原因候補「同じ行の変更」（解いて続ける）
- 結果: 成功=履歴を整えた ／ 未達=前後の図を示す
- まとめ: ①rebase は付け替え ②ID が変わる ③共有した枝ではしない ／ 次: git.a.02

### git.i.06 .gitignore とタグ（設定・中級）
- 解説: 何か=管理しない物を決める .gitignore と、版に名前を付けるタグ ｜ なぜ=生成物や秘密を入れない・リリースの版を示す ｜ 何に=リポジトリの整理・リリース ｜ 場面=node_modules がリポジトリに入りそう
- 図: 管理する物としない物と、v1.0 のタグ
- 理解: [状況説明] 入れてはいけない物を選ぶ ／ [用語] タグとブランチの違い
- クイズ: [選択] 管理しない → 生成物・秘密・依存の置き場 ／ [原因特定] .gitignore に書いたのに追跡される → 既に追跡済み ／ [状況判断] リリースの版 → タグ
- 実戦（端）: 目的=生成物と .env を外し、v1.0 のタグを付ける ／ 達成=status に出ず、タグがある ／ ヒント=①書く場所 ②追跡済みを外す ③.gitignore と git tag v1.0 ／ エラー=まだ出る→原因候補「既に追跡済み」
- 結果: 成功=リポジトリを整えた ／ 未達=追跡の状態を示す
- まとめ: ①入れない物は .gitignore ②追跡済みは外す必要がある ③版にはタグ ／ 次: cicd.b.04

### git.a.01 壊れた変更を探す（調査・上級）
- 解説: 何か=bisect で原因の記録を半分ずつ絞る、blame で行ごとの最後の変更を見る ｜ なぜ=多くの記録から原因を早く見つける ｜ 何に=障害の原因調査 ｜ 場面=100 件前は動いていた
- 図: 良い版と悪い版の間を半分ずつ絞る
- 理解: [結果予測] 100 件を絞るのに要る回数 → 約 7 回 ／ [用語] bisect と blame を結ぶ
- クイズ: [状況判断] いつから壊れたか分からない → bisect ／ [状況判断] この行は誰がなぜ → blame ／ [並べ替え] start → bad → good → 繰り返し ／ [結果予測] 100 件を半分ずつ絞る → 約 7 回で特定
- 実戦（端）: 目的=テストを壊した記録を特定する ／ 達成=正しい記録 ／ ヒント=①始める ②良い・悪いを伝える ③bisect の手順 ／ エラー=違う→原因候補「良い・悪いの判定を誤った」
- 結果: 成功=原因の記録を特定 ／ 未達=絞り込みの経過を示す
- まとめ: ①半分ずつ絞る ②行の履歴は blame ③判定を正確に ／ 次: trouble.a.02

### git.a.02 チームのブランチ戦略（運用・上級）
- 解説: 何か=枝の作り方・保護・レビュー・リリースの決まり ｜ なぜ=人が増えても壊さずに速く進める ｜ 何に=チーム開発の設計 ｜ 場面=main に直接入れて本番が壊れた
- 図: 短い枝 → 依頼 → 検査と承認 → 保護された main → タグでリリース
- 理解: [並べ替え] 変更が本番に届く流れ ／ [状況説明] 保護が無い時の事故
- クイズ: [状況判断] main を守る → 保護と必須の検査 ／ [選択] 枝の寿命 → 短く ／ [原因特定] 衝突が多い → 枝が長すぎる
- 実戦（模）: 目的=チームの決まりを設計し、保護を設定する ／ 達成=直接の push が拒否され、承認と検査が必須 ／ ヒント=①守る枝 ②必須の条件 ③設定の組み合わせ ／ エラー=直接入れられる→原因候補「保護の対象を誤った」
- 結果: 成功=壊れにくい流れを作った ／ 未達=抜けた決まりを示す
- まとめ: ①短い枝 ②main を保護 ③検査と承認を必須に ／ 次: cicd.a.03, devops.a.02

### git.a.03 秘密情報をコミットしてしまったら（事故・上級）
- 解説: 何か=無効化 → 履歴からの除去 → 再発防止の順に対処すること ｜ なぜ=消すだけでは履歴と複製に残る ｜ 何に=事故対応 ｜ 場面=API のトークンを push してしまった
- 図: 3 段の流れと、各段でしてはいけない事
- 理解: [並べ替え] 3 段の順 ／ [はい・いいえ] ファイルを消してコミットすれば安全 → いいえ
- クイズ: [状況判断] 最初の一手 → トークンを無効化 ／ [結果予測] 削除のコミット → 履歴に残る ／ [選択] 再発防止 → .gitignore と秘密の検査
- 実戦（端）: 目的=漏れたトークンを無効化し、履歴から除き、検査を入れる ／ 達成=新しいトークンで動き、履歴に無く、検査が働く ／ ヒント=①無効化 ②履歴を書き換える道具 ③3 段の手順 ／ エラー=まだ履歴にある→原因候補「全ての枝とタグを書き換えていない」
- 結果: 成功=順に対処できた ／ 未達=残っている場所を示す
- まとめ: ①無効化が先 ②履歴から除く ③検査で再発を防ぐ ／ 次: sec.a.03
