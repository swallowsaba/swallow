# レッスン設計: コンテナ（ctr）— コンテナ施設

書式は `docs/lessons/README.md`。**コンテナの概念を先に教え、Docker は具体例として `docker.md` で扱う。**

### ctr.b.01 コンテナとは（なぜ必要か）（考え方・初級）
- 解説: 何か=アプリと、動くのに必要な物一式を箱に詰めて動かす仕組み ｜ なぜ=「自分の PC では動いた」問題を無くし、どこでも同じに動かす ｜ 何に=配布・開発環境・規模の拡大 ｜ 場面=同僚の PC でだけ動かない
- 状況説明: 開発者の PC では動くアプリが、ライブラリの版の違いで本番では動かない
- 図: アプリ・ライブラリ・設定を箱に入れ、どの機械でも同じ箱を動かす
- 理解: [図] 箱に入る物を選ぶ（アプリ・ライブラリ・設定。カーネルは入らない） ／ [用語] イメージとコンテナを結ぶ
- クイズ: [用語] コンテナはカーネルを含むか → 含まない ／ [状況判断] 同じ環境を 10 台に → 同じイメージから動かす ／ [結果予測] 同じイメージから 3 つ → 同じ中身の 3 つ
- 実戦（模）: 目的=依存の違いで動かない 3 台を、同じ箱で動かす（アプリ・ライブラリ・設定・カーネルの札を「箱（イメージ）」と「それぞれの機械に任せる」の枠へドラッグして置く） ／ 達成=3 台とも動く ／ ヒント=①何が違うか ②箱に入れる物 ③箱を配る ／ エラー=1 台だけ動かない→原因候補「設定を箱に入れていない」、カーネルを箱へドラッグ→枠が赤く光り「カーネルは箱（イメージ）に入らない」の理由が出る（原因候補「OS の全てを箱に入れると考えた」）
- 結果: 成功=箱ごと運ぶ意味を理解 ／ 未達=違いの一覧を示す
- まとめ: ①箱ごと運べば同じに動く ②設計図がイメージ、実体がコンテナ ③Docker はこれを扱う道具の 1 つ ／ 次: ctr.b.02, ctr.b.03

### ctr.b.02 VM との違い（比較・初級）
- 解説: 何か=仮想マシンは OS ごと、コンテナはカーネルを共有してアプリだけを分ける ｜ なぜ=軽さ・起動の速さ・分け方の強さが違う ｜ 何に=使い分けの判断 ｜ 場面=1 台で 50 個のアプリを動かしたい
- 図: VM（各々が OS を持つ）とコンテナ（カーネルを共有）の積み木の比較
- 理解: [関係性] 共有する物 → カーネル ／ [はい・いいえ] コンテナは VM より起動が速い → はい
- クイズ: [状況判断] 別の OS を動かしたい → VM ／ [状況判断] 同じ OS で多数のアプリ → コンテナ ／ [結果予測] カーネルの欠陥 → 全コンテナに影響し得る ／ [用語] 仮想マシン → OS ごと分けた機械
- 実戦（模）: 目的=4 つの要件に VM とコンテナを選ぶ ／ 達成=理由付きで正しい ／ ヒント=①OS が違うか ②数と速さ ③答え ／ エラー=取り違え→原因候補「分け方の強さを考えていない」
- 結果: 成功=使い分けられた ／ 未達=比較表を示す
- まとめ: ①VM は OS ごと ②コンテナはカーネルを共有 ③要件で選ぶ ／ 次: ctr.b.03

### ctr.b.03 イメージとコンテナ（イメージ・初級）
- 解説: 何か=変わらない設計図（イメージ）と、それから作る動く実体（コンテナ） ｜ なぜ=同じ設計図から何個でも同じ物を作れる ｜ 何に=配布・拡大 ｜ 場面=コンテナの中で直した設定が、作り直すと消えた
- 図: 1 つのイメージから 3 つのコンテナ。コンテナの変更はイメージに戻らない
- 理解: [関係性] イメージとコンテナ → 1 対 多 ／ [はい・いいえ] コンテナ内の変更でイメージも変わる → いいえ
- クイズ: [結果予測] コンテナを消して作り直す → 中での変更は消える ／ [状況判断] 変更を残したい → イメージを作り直すか、外に保存 ／ [用語] イメージ → 変わらない設計図
- 実戦（端）: 目的=予約の窓口のコンテナ `web`（イメージ `reserve:1.0`。この機械の道具は Podman）の閉館の時刻を 17:00 から 19:00 にし、作り直しても残る直し方を確かめる ／ 達成=①`podman exec web sed -i` で中を直し、`podman restart web` と `curl` で 19:00、`podman diff web` に `C /app/server.js` ②`podman rm -f web` と `podman run` で同じイメージから作り直すと 17:00 に戻る ③設計図の `~/reserve/server.js` を直し `podman build -t reserve:1.1 reserve` で作った新しいイメージから作り直すと 19:00 で、`podman diff` は空 ／ ヒント=①`podman exec` と `sed -i` ②作り直しの元はいつもイメージ ③元のファイルを直して新しいタグで作る ／ エラー=`the container name is already in use`→原因候補「前のコンテナを消していない」、`as it is running`→原因候補「`-f` を付けずに消した」、`address already in use`→原因候補「前のコンテナが同じポートで動いている」
- 結果: 成功=設計図と実体を区別 ／ 未達=変更の行き先を示す
- まとめ: ①イメージは設計図 ②コンテナは実体 ③変更は設計図か外に残す ／ 次: ctr.b.04, ctr.b.05

### ctr.b.04 レイヤ（レイヤ・初級）
- 解説: 何か=イメージを重ねた層で作る仕組み ｜ なぜ=共通の層を共有して、容量と転送を節約する ｜ 何に=イメージの軽量化・作る速さ ｜ 場面=小さな変更なのに毎回大きな転送が起きる
- 図: 土台の OS の層 → ライブラリの層 → アプリの層。2 つのイメージが下の層を共有
- 理解: [図] 共有される層を塗る ／ [関係性] 変更した層より上は作り直し
- クイズ: [結果予測] アプリの層だけ変える → 下の層は再利用 ／ [状況判断] 変わりやすい物 → 上の層に置く ／ [原因特定] 毎回全部作り直す → 変わりやすい物が下の層にある
- 実戦（編）: 目的=`~/reserve/Containerfile` の命令の順を直し、コードだけを直した時に `RUN npm install` の層を使い回す。保存すると `podman build -t reserve:1.1 .`、`server.js` を 1 行直して `podman build -t reserve:1.2 .` が走る ／ 達成=最後の作り直しで `RUN npm install` に `--> Using cache` が出る（`cached:reserve:1.2=npm`） ／ ヒント=①段の中身が変わるとその後は全て作り直し ②`COPY . .` を `COPY package.json .` と `COPY server.js .` に分ける ③完成した Containerfile ／ エラー=`RUN npm install` が作り直された→原因候補「`COPY . .` が上にある」、`while running runtime`→原因候補「`package.json` を写す前に `npm install`」、`copier: stat`→原因候補「写すファイルの名前の誤り」、`parsing containerfile`→原因候補「命令の綴りの誤り」
- 結果: 成功=層を活かせた ／ 未達=作り直された層を示す
- まとめ: ①イメージは層の重なり ②下の層を共有 ③変わりやすい物は上に ／ 次: ctr.i.01, docker.i.01

### ctr.b.05 レジストリ（レジストリ・初級）
- 解説: 何か=イメージを置いて配る場所。名前とタグで指す ｜ なぜ=どの機械からも同じイメージを取れる ｜ 何に=配布・共有 ｜ 場面=本番のサーバにイメージを届けたい
- 図: 作る機械 → レジストリ → 動かす機械たち。名前:タグ の読み方
- 理解: [図] registry.example/shop/web:1.2 を部品に分ける ／ [はい・いいえ] タグを省くと必ず最新の安定版 → いいえ（latest という名前のタグを指すだけ）
- クイズ: [用語] タグ → 版の名札 ／ [原因特定] 取れない → 名前やタグの誤り、または認証 ／ [状況判断] 本番の指定 → 固定したタグ
- 実戦（端）: 目的=本番の機械 `shop-prod`（Podman）で、タグを書かずに動かしたコンテナ `shop` の版を調べ、検証で確かめた版に固定する ／ 達成=①`podman ps` の `IMAGE`（`:latest`）・`podman search --list-tags registry.city.example/shop/web`・`podman pull …:1.3-rc1` と `podman images` の `IMAGE ID` から、`latest` が `1.3-rc1` と同じ中身だと答える ②`podman rm -f shop` と `podman run -d --name shop -p 8080:3000 registry.city.example/shop/web:1.2` で「予約を確定する」が戻る ／ ヒント=①タグを省くと latest ②タグは名札。同じ中身かは IMAGE ID ③タグを書いて作り直す ／ エラー=答えが違う→原因候補「latest をそのまま答えた」「最新の安定版と考えた」、`manifest unknown`→原因候補「タグの綴り（v1.2）」、`name unknown`→原因候補「名前の打ち間違い」、`authentication required`→原因候補「ログインしていない」
- 結果: 成功=名前とタグで指せた ／ 未達=部品を示す
- まとめ: ①レジストリはイメージの置き場 ②名前:タグで指す ③本番は版を固定 ／ 次: docker.i.05, cicd.b.04

### ctr.i.01 コンテナランタイム（ランタイム・中級）
- 解説: 何か=コンテナを実際に動かす部品と、その標準（OCI） ｜ なぜ=道具が違っても同じイメージを動かせるのは標準があるから ｜ 何に=Docker・Kubernetes・Podman の関係の理解 ｜ 場面=Kubernetes は Docker 無しでコンテナを動かしている
- 図: 利用者の道具（Docker・Podman・Kubernetes）→ 高い層のランタイム（containerd など）→ 低い層（runc）→ カーネル
- 理解: [図] 各道具を層に置く ／ [関係性] OCI の役割 → イメージと実行の標準
- クイズ: [用語] OCI → コンテナの標準 ／ [結果予測] Docker で作ったイメージを Kubernetes で → 動く ／ [選択] Kubernetes がよく使うランタイム → containerd
- 実戦（模）: 目的=3 つの環境の構成図を完成させる ／ 達成=全て正しい ／ ヒント=①上から ②標準でつながる ③配置 ／ エラー=取り違え→原因候補「Docker を必須と考えた」
- 結果: 成功=道具の関係を整理 ／ 未達=層の図を示す
- まとめ: ①標準があるから入れ替えられる ②Docker は道具の 1 つ ③Kubernetes は Docker 無しでも動く ／ 次: ctr.i.02, docker.a.03

### ctr.i.02 隔離の仕組み（隔離・中級）
- 解説: 何か=見える範囲を分ける名前空間と、使える量を制限する cgroups ｜ なぜ=コンテナどうしが互いに見えず、資源を奪い合わないため ｜ 何に=安全と安定 ｜ 場面=1 つのコンテナがメモリを使い切った
- 図: 名前空間（プロセス・網・ファイル）の壁と、cgroups の量の上限
- 理解: [用語] 名前空間と cgroups を役割に結ぶ ／ [状況説明] 上限が無い時の事故
- クイズ: [結果予測] コンテナ内の ps → 自分のプロセスだけ ／ [状況判断] 使い切りを防ぐ → メモリの上限 ／ [原因特定] 上限を超えた → 止められる
- 実戦（端）: 目的=コンテナの中と外でプロセスの見え方を比べ、メモリの上限を設定する ／ 達成=違いを回答し、上限が効く ／ ヒント=①中と外の ps ②上限の指定 ③答えと設定 ／ エラー=止められる→原因候補「上限が低すぎ」
- 結果: 成功=隔離の 2 本柱を理解 ／ 未達=見え方の差を示す
- まとめ: ①名前空間で見える範囲を分ける ②cgroups で量を制限 ③VM ほど強くはない ／ 次: ctr.a.01, k8s.i.07

### ctr.i.03 コンテナのネットワーク（ネットワーク・中級）
- 解説: 何か=コンテナに付く網と、外やほかのコンテナとの通り道 ｜ なぜ=コンテナは閉じた箱で、つなぎ方を決めないと届かない ｜ 何に=Web と DB をつなぐ・外に公開する ｜ 場面=Web のコンテナから DB のコンテナに届かない
- 図: 仮想の網に 2 つのコンテナ。外への公開は扉の対応
- 理解: [関係性] 同じ網のコンテナ → 名前で届く ／ [状況説明] 公開しないと外から届かない
- クイズ: [原因特定] 届かない → 別の網にいる ／ [状況判断] DB を外に公開するか → しない ／ [結果予測] localhost はコンテナ内で → そのコンテナ自身
- 実戦（端）: 目的=機械 `reserve-01`（Podman）で、`front-net` の `web` が DB の場所 `localhost:5432` のせいで止まっている。`back-net` にいて 5432 番を公開している `db` とつなぎ、外には `web` だけを公開する ／ 達成=①`podman logs web` の `ECONNREFUSED 127.0.0.1:5432` から、`localhost` が指したコンテナ（`web`）を答える ②`podman network connect front-net db`、`web` を `--network front-net -p 8080:3000 -e DATABASE_URL=postgres://postgres@db:5432/reserve` で作り直し、`curl` で予約の数 ③`db` を `-p` 無しで `front-net` に作り直し、`podman port db` が空 ／ ヒント=①記録の最後の行 ②同じ自作の網なら名前で届く ③公開は作る時の `-p` ／ エラー=`ECONNREFUSED 127.0.0.1`→原因候補「localhost のまま」、`ENOTFOUND`→原因候補「別の網」「既定の網に入れた」、`ETIMEDOUT`→原因候補「アドレスで指した」、`unable to find network`→原因候補「網の名前の誤り」
- 結果: 成功=通り道を設計 ／ 未達=網の図を示す
- まとめ: ①同じ網なら名前で届く ②外へは公開が必要 ③localhost は自分 ／ 次: docker.i.04, ctr.i.05

### ctr.i.04 コンテナとデータ（ストレージ・中級）
- 解説: 何か=消える領域（コンテナの中）と残す領域（ボリューム） ｜ なぜ=コンテナは作り直す前提。データを中に置くと消える ｜ 何に=DB・アップロードされたファイル ｜ 場面=更新したら DB の中身が消えた
- 図: コンテナの中の書き込み層と、外に置いたボリューム
- 理解: [関係性] 作り直しと消える物 ／ [はい・いいえ] DB のデータはコンテナの中に置く → いいえ
- クイズ: [結果予測] ボリューム無しで作り直す → データが消える ／ [状況判断] 残す物 → ボリューム ／ [原因特定] 更新で消えた → 中に置いていた
- 実戦（端）: 目的=機械 `reserve-01`（Podman）で、ボリューム `db-data` を `/data` に付けて動かしている DB のコンテナ `db` を、作り直しても予約が残るようにする ／ 達成=①`podman inspect db` の `Mounts` と `psql -c 'SHOW data_directory'`・`podman exec db ls` から、DB が書く場所（`/var/lib/postgresql/data`）を答える ②`-v db-data:/var/lib/postgresql/data` で作り直し（試しの予約は消えて 3 件）、`INSERT` で 4 件にする ③もう一度作り直し、`podman logs db` に `Skipping initialization`、`SELECT count(*)` が 4 ／ ヒント=①付けた場所と書く場所 ②`-v ボリューム:中の場所` ③同じボリュームを同じ場所に付けて作り直す ／ エラー=答えが違う→原因候補「付けた場所を答えた」「手元の置き場所を答えた」、`does not exist`→原因候補「psql の DB・利用者の名前の誤り」
- 結果: 成功=残す設計 ／ 未達=データの行き先を示す
- まとめ: ①中は消える ②残す物はボリューム ③付ける場所を正しく ／ 次: docker.i.03, k8s.i.03

### ctr.i.05 複数コンテナで 1 つのサービス（複数・中級）
- 解説: 何か=役割ごとにコンテナを分けて組み合わせる設計 ｜ なぜ=別々に更新・拡大でき、壊れても範囲が狭い ｜ 何に=Web・API・DB の構成 ｜ 場面=全部を 1 つのコンテナに入れていて更新が大変
- 図: 1 つに全部入れた形と、役割で分けた形
- 理解: [関係性] 分ける利点 ／ [状況説明] 1 つに入れた時の問題
- クイズ: [状況判断] API だけ増やしたい → 分けておく ／ [選択] 1 つのコンテナに入れる単位 → 1 つの役割 ／ [結果予測] DB が落ちる → Web は動くが一部の機能が止まる
- 実戦（編）: 目的=画面・API・DB を 1 つのコンテナに詰めた `city-reserve-all:1.0` の `~/reserve/compose.yaml` を、`web`（`city-reserve-ui:1.0`。API の場所は `API_URL`）・`api`（`city-reserve-api:1.0`。DB の場所は `DATABASE_URL`）・`db`（`city-db:1.0`）の 3 つのサービスに書き直す。保存すると `podman compose up -d`・`ps -a`・`logs`・`curl` が走る ／ 達成=①3 つのサービスが役割ごとのイメージで作られ、公開は `web` の 8080 番だけ（`localhost` のままだと `api` は止まり、`web` は 502） ②相手をサービスの名前（`http://api:3000`・`db:5432`）で指し、`depends_on` を書いて、8080 番が予約の数を答える ／ ヒント=①1 つのサービスに 1 つの役割 ②分けた後の localhost は自分 ③完成した compose.yaml ／ エラー=`ECONNREFUSED 127.0.0.1`→原因候補「localhost のまま」、`ENOTFOUND`→原因候補「サービスの名前の誤り」、`missing environment variable`→原因候補「environment の書き忘れ・字下げ」、`yaml: line`→原因候補「字下げのずれ」、`additional properties`→原因候補「項目の綴り」
- 結果: 成功=役割で分けた ／ 未達=つながりの図を示す
- まとめ: ①1 つの役割に 1 つのコンテナ ②別々に更新・拡大 ③つながりを設計 ／ 次: docker.i.06, k8s.b.01

### ctr.a.01 コンテナ運用（運用・上級）
- 解説: 何か=ログ・資源の制限・更新・再起動の方針を決めて運用すること ｜ なぜ=動かした後の方が長い ｜ 何に=本番の運用 ｜ 場面=夜中に落ちたコンテナが起き上がらない
- 図: 再起動の方針・ログの出し先・資源の上限・更新の手順
- 理解: [状況説明] 方針の無い時の事故 ／ [関係性] ログは標準出力へ → 集めやすい
