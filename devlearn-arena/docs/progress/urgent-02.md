# 至急 02: 実戦で、目的を果たした命令がエラー扱いになる不具合

記録した日: 2026-10-16

指示（URGENT.txt）の不具合を、`docs/development-plan.md` の Phase より先に直した。

## 症状

linux.b.04（探す）の実戦で `grep -r timeout /var/log | wc -l` を打つと、3 が正しく出るのに「エラーが出た。調べてみよう」と
`Permission denied` の案内が出ていた。

## 原因

### (a) 標準エラーに文が出ただけで、命令の失敗とみなしていた

`src/learning/practice.ts` の `afterCommand` は、標準エラーが空でなければ必ずエラーの案内を出していた。終了の状態も、結果（標準出力）も見ていなかった。
`grep -r` は読めない `/var/log/secure` を飛ばして続け、結果は標準出力に出す。パイプの終了の状態は最後の `wc -l` の物で 0。それでも、標準エラーに
`grep: /var/log/secure: Permission denied` が出たので案内が出た。2 つ目の手順の `find / -name app.conf` も同じだった（/root の `Permission denied`）。

あわせて、模擬の grep の終了の状態が本物と違っていた。一致があると、読めない場所があっても 0 を返していた。本物の GNU grep は、誤りがあれば一致があっても 2 を返す。

### (b) 答える欄の判定

判定そのものは正しく働いていた（答えだけで決まり、端末の出力に引きずられない）。前に案内が出ていても、正しい答えで手順を満たし、案内は消える。
ただ (a) のために、正しい命令を打つたびに案内が出て、出続けているように見えていた。1280×720 でも、案内が出ている間も答える欄は案内の上に見えていて、押せる。

## 再現するテスト（先に書いて、失敗を確かめた）

`src/learning/practice.test.ts` の「目的を果たした命令はエラーにしない」。実戦の画面と同じく、setup の run（chown・chmod）まで済ませた機械で打ち、
標準出力・終了の状態も渡す（テストの `player` を画面と同じ道筋にした）。

- `grep -r timeout /var/log | wc -l` は 3 を出し、`Permission denied` があっても案内を出さない。3 と答えて手順を満たす（直す前は案内が出て失敗した）
- パイプ無しの `grep -r timeout /var/log` は終了の状態が 2。結果の行が出ていれば案内を出さない（直す前は 0 が返って失敗した）
- `find / -name app.conf` は案内を出さず、場所を答えて全ての手順を満たす。記録のエラーは空（直す前は案内が出て失敗した）
- 読めないファイルだけを `grep` した（結果が無い）時は、目的を果たせていないので案内を出す
- 前に案内が出ていても、正しい答えは通る（(b) の確かめ）

`src/engines/kernel/commands/linuxCli.test.ts`: 一致があっても読めない場所があれば grep は 2。`| wc -l` を付けた行の終了の状態は 0。

## 直したこと

- `src/learning/practice.ts` に `failedCommand`（と、案内を探す時に使う `failureOf`）を足し、エラーの案内はこれが「目的を果たせなかった」と言う時だけ出す
  - 標準エラーが空 → 果たしている
  - 終了の状態が 0 → 果たしている（標準エラーの文は警告や途中経過。`curl -v`・`kubectl` の `Warning:`・パイプの前の命令が飛ばした場所）
  - 0 でなくても、結果（標準出力）が出ていて、エラーの行が全て「飛ばして続けた」物 → 果たしている
  - 1 行に `;` `&&` `||` で並べた時は区切りごとに確かめ、どれかが果たせなければ案内を出す（`cd /srv/ap; ls` は最後の `ls` が通っても、`cd` の誤りで案内を出す）。
    後ろが `||` の命令の失敗は、その行の中で受けているので数えない
  - 終了の状態の無い操作（画面の操作・SQL・設定の編集の確かめ）は、今までどおり標準エラーがあれば案内を出す
- 「飛ばして続けた」行は、エラーの解説のデータ `skipped`（正規表現）で持つ（`src/content/schema.ts`、`content/errors/linux.json` の `perm-denied-search` に
  `^(grep|find|du|ls): .+: Permission denied$`）。解説の `match` の `Permission denied` をそのまま使うと、`ssh-copy-id` の鍵が断られた
  `Permission denied (publickey)`（結果の行も出る・終了の状態 1）まで「飛ばした」と見てしまうので、行の形を分けた
- `src/engines/kernel/shell.ts`: 1 行の実行結果に、区切りごとの結果（`parts`）を足した。端末の画面（`TerminalView`・`useShellSession`）から実戦へ渡す
- `src/engines/kernel/commands/text.ts`: grep の終了の状態を本物と同じにした（誤りがあれば 2、無ければ一致で 0、無しで 1）
- 設定の編集: 保存の後に打つ行ごとに終了の状態を持ち（`EditResult.code`）、目的を果たせなかった行の標準エラーだけを案内に使う。
  記録し始める前の保存（`code` の無い物）も読み戻せる（`src/screens/lesson/savedPractice.ts`）
- 最後のヒントの再生（`replayAnswers`）も同じ `failedCommand` で確かめる
- `perm-denied-search` の文を、案内が出る場面（何も読めなかった時）に合わせた。「探す命令は飛ばして続けている」「結果は普通の行に出ている」は、
  今は案内が出ない場面の説明だったので、「そこからは何も読めず、結果が出なかった」「探す場所を広げてみよう」に直した

## 同じ作りの実戦の洗い出し

全てのレッスンとミッションの端末・設定の編集の実戦で、最後のヒントの答えを初めから順に打ち、ヒントの 1・2 段に出る命令もその時点の状態で打って、
標準エラーが出た物を全て調べた（一時の調べの台。使い終えて消した）。

答えの道筋で標準エラーが出た命令は 17 個。直した後、案内を出さなくなったのは linux.b.04 の `grep -r timeout /var/log | wc -l` だけだった。
残る 16 個は、どれも目的を果たせていない本当の失敗で、出会うこと自体が課題になっている（手順の想定エラーに書いてある）。案内を出すのが正しい。

| 実戦 | 命令 | 出る物 | 判定 |
|---|---|---|---|
| linux.b.04 count | `grep -r timeout /var/log \| wc -l` | 3 と Permission denied（終了 0） | **直した。案内を出さない** |
| linux.b.04 where | `find / -name app.conf`（2 段目のヒントの形。最後のヒントは 2>/dev/null 付きで標準エラーが出ない） | 場所と Permission denied（終了 1） | **直した。案内を出さない** |
| docker.b.01 client | `docker version` | 手元の版と、デーモンにつながらない（終了 1） | 失敗。デーモンが動いていないことを読む課題 |
| k8s.b.01 manual | `kubectl drain node-2` | cordoned と、断った理由（終了 1） | 失敗。飛ばしたのでなく断った |
| git.b.06・git.i.02・mission git-history | `git merge` `git pull` | 衝突（終了 1） | 失敗。衝突を解く課題 |
| git.i.02 look | `git push` | rejected（終了 1） | 失敗 |
| git.i.05 start | `git rebase main` | 衝突（終了 1） | 失敗 |
| mon.b.04 condition | `promtool test rules ...`（保存の後） | FAILED（終了 1） | 失敗。試験が落ちたことを読む課題 |
| net.b.03 read | `ping -c 1 192.168.10.1` | Network is unreachable（終了 2） | 失敗 |
| net.b.04 web | `systemctl restart nginx` | 起動に失敗（終了 1） | 失敗 |
| net.i.02 look | `ip netns exec outside curl ...` | 時間切れ（終了 28） | 失敗 |
| trouble.b.02（5 つ） | `cat` `curl` `sh build.sh` | 読めない・無い・断られた・時間切れ・作れない | 失敗。エラーの種類を読み分ける課題 |

指示にあった例の確かめ:

- grep・find の Permission denied: 上の 2 つ。どちらも結果が出ていれば案内を出さない。読める所に何も無い時だけ出す
- curl の一部の失敗: 模擬の curl は 1 回に 1 つの宛先で、つながらなければ結果を出さない（終了 7・28）。一部だけ失敗する形は無い。
  `curl -v` の途中経過（標準エラー・終了 0）は、今まで案内が出ていたが出さなくなった。`-v` と `-i` で 403 を見た時は、手順の想定エラーにあれば、出力の解説（`output`）が当たる
- kubectl の警告: 模擬の `kubectl drain` の `Warning:` は出力に出る（案内は出ない）。標準エラーに出る警告が来ても、終了 0 なら案内を出さない。
  断った時（終了 1）は、結果の行があっても案内を出す
- そのほか: `ssh-copy-id` の「全ての鍵が既にある」WARNING（終了 0）と、`dhcpd` の起動の文（標準エラー・終了 0）は案内を出さなくなった。
  `ssh-copy-id` の鍵が断られた時（終了 1）は今までどおり出す

## 仕様書に書いたこと

- `docs/learning-design.md` 7 章: 「エラーの案内は、コマンドが目的を果たせなかった時だけ出す。警告や、読めない場所を飛ばしただけの時は出さない」と、出す・出さないの場合分け。答える欄の判定は答えだけで決めること
- `docs/content-spec.md` 2.5: 同じ決まりと、解説の `skipped`（飛ばして続けた行の正規表現）。想定エラーに書いても、目的を果たした命令では案内を出さないこと

## 画面で確かめたこと

`tools/scenarios/search.mjs`（1920×1080 と 1280×720）で linux.b.04 の実戦を通して撮り、開いて確かめた。

- `u2-grep`: `grep -r timeout /var/log | wc -l` を打つと、端末に赤い `grep: /var/log/secure: Permission denied` と `3` が出る。**エラーの案内は出ない**。下に答える欄と、今打てるコマンドの候補が見える
- `u2-count-done`: 答える欄に 3 を入れると、1 つ目の手順に印が付き「何が起きたか」が出る。案内は出ない
- `u2-find`・`u2-done`: `find / -name app.conf` でも案内は出ない。場所を答えると 2 つの手順に印が付き「達成した」。「結果へ」が押せる
- `u2-cat-denied`（比べる）: 読めない `/var/log/secure` を `cat` すると、結果が無いので案内が出る。内容は「そこからは何も読めず、結果が出なかった」と、場面に合った文になっている。
  1280×720 でも、答える欄は案内の上に見えている
