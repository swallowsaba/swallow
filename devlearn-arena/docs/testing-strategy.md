# テスト戦略

完成条件は `docs/acceptance-criteria.md`。この文書は**どう確かめるか**を決める。

## 1. 共通

- コミットの前に `npm run typecheck` `npm run lint` `npm run test` を通す
- 不具合は、先に再現する失敗するテストを書いてから直す
- 振る舞いを確かめる。部品が存在するだけのテストは書かない
- 新しい部品が呼ばれているか（import され、画面に出るか）を確かめる。存在するだけでは未完成

## 2. 単体テスト（Vitest）

| 対象 | 確かめること |
|---|---|
| `src/city` | 座標変換・描画順・配置の判定・道路のつながり・区画の成長・同じ seed で同じ結果 |
| `src/game` | XP の表（稼ぎ防止を含む）・スキルの式・発展段階の判定 |
| `src/learning` | 段の遷移・クイズの判定・推奨の計算・知識グラフ・復習の間隔 |
| `src/engines/*` | 各コマンドと模擬環境の状態変化・エラーの出方 |
| `src/save` | 保存と復元の往復・版の移行（版 3 → 4 を含む。10.5）・壊れたデータの拒否 |
| `src/sim` | 都市の模擬と市政（10 章） |
| 層の境界 | 純粋な層（`src/sim` を含む）が React・DOM・Canvas を import していない。`src/sim` が `Math.random`・`Date.now` を使わない。学習の側が `src/sim` を読まない（ESLint と、念のためのテスト） |
| 見た目の規則 | `src/ui/**` `src/screens/**` に生の色・指定外の文字の大きさ・絵文字が無い |

## 3. コンテンツの検査

`docs/content-spec.md` 6 章の全項目。特に:

- 全レッスンが 7 段を持つ
- 推奨前提の循環が無い。**ロックの仕組みがどこにも無い**（「始める」が常に押せる）
- 用語集に無い専門用語が本文に無い
- 全実戦の最後のヒントで達成条件を満たす

## 4. 統合テスト

- 学習記録 → XP・スキル・資金 → 都市の状態、の一連の計算
- ミッションの達成 → 報酬 → 都市
- 保存 → 再読み込み → 同じ状態
- 都市の模擬と市政の連鎖（10.5）

## 5. UI テスト（Testing Library と Playwright）

- 部品: 情報パネル・入口の札・クイズ・用語の小窓・エラーの小窓の表示と操作
- E2E（Playwright）: `docs/acceptance-criteria.md` 1 章のゲームループを 1 本の E2E で通す
- キーボードだけでの操作・明るさの差の自動検査

## 6. 画面の確認（撮影）

**UI は「動いた」だけで完成にしない。**

- 撮影は Playwright で行う。Phase 1 で `npm run shoot -- <名前> <パス>`（1920×1080、保存先 `shots/`）を作る
- 撮った画像を**自分で開いて**、`docs/visual-design.md` 8 章の V1〜V11 を 1 つずつ確かめ、結果を `docs/progress/phase-<番号>.md` に書く
- 動きの確認: 2 秒あけて 2 枚撮り、差があることを確かめる（車・人・施設の動き）

## 7. 学習フローのテスト

- 最初に作るレッスン（found.b.04 と linux.i.01）で、7 段を通す E2E。以後、分野ごとに 1 本を加える
- 誤った入力 → エラーの案内 → ヒント → 成功、の E2E
- 前提を学ばずに上級のレッスンを始められること

## 8. セーブのテスト

- 自動保存の後にリロードして同じ状態
- 書き出したファイルを別のブラウザの状態で読み込んで同じ状態
- 古い版のファイルが移行されること。壊れたファイルで既存のデータが消えないこと

## 9. 公開環境のテスト

- `npm run build` の結果を `npm run preview` でサブディレクトリ（`/swallow/devlearn-arena/`）配信して E2E
- 公開後、公開 URL に対して E2E と撮影
- 直リンク（`#/learn/linux.i.01`）とリロード
- 秘密情報の検査（gitleaks などの無料の道具、または `tools/secret-scan.mjs` の簡易検査）を CI で実行

## 10. 都市の模擬と市政のテスト

仕組みは `docs/game-design.md` 13〜27 章（`docs/decisions.md` D-20）、完成条件は `docs/acceptance-criteria.md` 7 章。

### 10.1 決定性（同じ種から同じ結果）

- **同じ seed・同じ命令の列（何日目に何をしたか）からは、同じ状態になる。** 見本の都市（村・町・地方都市の 3 つ。`src/sim/__fixtures__/`）に決めた命令の列を与えて 2 年分を 2 回流し、保存データの形（`docs/data-model.md` 12 章）に直した物が深く等しいことを確かめる
- 命令の列の順を 1 つ入れ替えると、結果が変わることも確かめる（命令が本当に効いている）
- 速さ（1 倍・3 倍）と、途中で止める・再開する・保存して読み込んで続けることで、結果が変わらない（命令は日の区切りで当たる。`docs/architecture.md` 9.1）
- Worker で流した結果と、同じ関数を直接呼んだ結果が等しい（Playwright の中で Worker を使い、Vitest で直接呼んで、同じ命令の列の結果の要約（人口・支持率・反対率・採決・財政）を比べる）
- **反対率・支持率に乱数を使わない**: `src/sim` が `Math.random`・`Date.now` を使わないことを、ESLint（層の境界）と念のためのテストで確かめる。seed から作る乱数を使ってよい所（地区の名前・同じ優先の請願の選び・見た目の変化）以外で乱数の関数を呼んでいないことを、呼び出しの数を数えるテストで確かめる（seed を変えても、地区の名前以外の数字が変わらない見本で確かめる）

### 10.2 単体テスト（`src/sim`）

| 対象 | 確かめること |
|---|---|
| 住民・家賃・引っ越し | `docs/game-design.md` 13.2・13.5 の表と式（例の 6 万円・負担 33%・40% を超えた層が週 5% 出ていく） |
| 地価・騒音 | 足し算の項ごとの値と原因。発生源からの距離で薄まる。譲歩の性質（`mods`）で変わる |
| 雇用と通勤 | 収入の帯の合う仕事に近い順に入る。混み具合で通勤時間が延びる。失業率 |
| 満足と支持率 | 13.8 の要因の点の表・層の重み・1/4 の近づき方・信頼の動きと戻り方 |
| 内訳 | 支持率の変化が、要因 × 原因の内訳の合計と一致する（足し算でない需給の倍率も、原因に分けた合計が一致する） |
| 説明の文 | 決めた内訳から決まった文になる。変化が 1 未満の文。数字が内訳と同じ |
| 申請 | 申請の対象の判定・段階と日数・費用の取り分けと戻し・6 件まで・28 日・同意の案件・完成するまで模擬に数えない |
| 反対 | 強さの計算（全ての `Measure`）・反対率と内訳の一致・距離と層の構成と組織化の係数で変わる |
| 公聴会 | 譲歩の効き（模擬の値が変わる）・説明の質ごとの効きと誤解の分の上限・段階による候補の出し分け・押し切るの政治資本と信頼 |
| 議会・申し立て | 議員の点の式（表で固定）・4 以上で可決・説得の上限・申し立ての条件と 28 日と取り下げ |
| 選挙・任期・公約・政治資本 | 投票率と得票率の式・敗因の組み立て・公約の判定・政治資本の得る・使う・上限 |
| 請願・予算・新聞 | 届く条件の式・優先と seed の選び・26 週・受理の中身の効き・税収と支出の式・赤字の効き・不祥事の条件・型の文の差し込み |
| 需要・電力・公共サービス | 需要の式・道路網に沿う送電・輪番の順・行き届きの距離と定員 |
| 褒賞・始め方 | 節目の判定（下がっても残る）・効き・始め方ごとの係数と境と初めの政治資本 |

- 表と式の値は `docs/game-design.md` の表を正とし、テストで固定する。値を変える時は、先に game-design を直してからテストを直す

### 10.3 学習にロックが無いこと

- 市政のどの状態（申請中・公聴会の途中・申し立て中・赤字・停電・選挙の画面の後・落選の後）からも、レッスン・ミッション・学習ライブラリを開けることを E2E で確かめる（`docs/acceptance-criteria.md` S2）
- スキル 0 のまま、譲歩と政治資本だけで申請を可決させる E2E（S3）
- 学習の側（`src/learning`・`src/engines`）が `src/sim` を import していないことを層の境界の検査で確かめる（`docs/architecture.md` 3 章）
- 落選の後の 2 つの道で、学習の記録（XP・スキル・レッスンの進み・ミッション）が同じであることを確かめる（S15）

### 10.4 コンテンツの検査

- `docs/content-spec.md` 6 章の市政のデータの項目（`src/content/politics.test.ts`）。特に、全ての理由に `requires` の無い譲歩があり、それが理由の元の値を下げること

### 10.5 統合テストと E2E

- 統合: 施設の完成 → 雇用 → 空き室 → 家賃 → 引っ越し → 支持率、の連鎖を見本の都市で流し、各段の値が動く向きを確かめる（S4）
- 統合: 申請 → 反対 → 公聴会の手 → 採決 → 完成 → 模擬の値、を命令の列で流す
- E2E: 市政のゲームループ（`docs/acceptance-criteria.md` 7.1 の S1）を 1 本で通す。時間は 3 倍にし、待つ所は時間を進める道具（開発の時だけ使える、日を進める命令。公開する build には入れない）で縮める
- E2E: 版 3 の保存データを読み込んで版 4 に移る（S29）。書き出し・読み込みで市政の状態が戻る

### 10.6 性能

- `tools/bench-sim.mjs`（`docs/architecture.md` 9.3）で、最も重い都市の 1 日・1 週・申請の見込みの時間を測り、`docs/progress/phase-g1.md` と `phase-g12.md` に記録する。目安を超えたら、次の Phase に進まない
- 都市画面の fps を、3 倍の速さ・最も重い都市・ヒートマップを重ねた形で、1920×1080 で測る（S28）。6 章の撮影と同じ Playwright で、2 秒の間のフレームの数を数える

### 10.7 画面の確認（撮影）

- 6 章の手順で、新しい窓（`docs/ui-design.md` 10・11 章）を全て 1920×1080 と 1280×720 で撮り、V1〜V11 を確かめる
- 都市画面の常時の UI の割合を、上の帯に物を足した Phase ごとに測る（`tools/scenarios/inspect.mjs`。S26）
- 申請の段階ごとの敷地・停電の地区・ヒートマップを撮り、見て分かることを確かめる
- Permit Pending の画面と並べて写していないことを確かめる（S27。見比べるのは仕組みの一覧だけで、画像を置かない）
