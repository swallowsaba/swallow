# レッスンの手本（各分野 1 本）

各分野について、分野 → テーマ → レッスン → 解説 → 理解 → クイズ → 実戦 → 結果 → まとめ まで設計した完成形。
コンテンツを作るときの手本にする。データ形式は `docs/content-spec.md`。

書式: **解説**は 4 つの問い（何か・なぜ・何に・どんな場面）、**理解**は 2 種類以上、**クイズ**は 3 種類以上、
**実戦**は目的・初期状態・達成条件・ヒント 3 段・想定エラー、**結果**は成功時と失敗時、**まとめ**は要点 3 つと次に学ぶこと。

## found.b.04 ファイルとディレクトリ（IT 基礎 / ファイル）

- **解説**
  - 何か: コンピュータの中の資料（ファイル）と、資料を入れる棚（ディレクトリ）。棚の中に棚を作れる木の形
  - なぜ: 数万の資料を名前だけで探すと、同じ名前の資料を取り違える
  - 何に: 資料の場所を「住所（パス）」で正確に指す
  - どんな場面: 設定ファイルを直す、ログを探す、アプリを置く
  - 状況説明: 2 つのディレクトリに同じ名前の設定ファイルがあり、違う方を直してしまう
- **理解**: 図の木で「/home/minato」を押して示す（図）／「パス」と「住所」、「ディレクトリ」と「通り」を結ぶ（用語確認）
- **クイズ**
  1. 用語理解: 「/」は何を表すか → 木の根（ルート）
  2. 結果予測: /home で `cd minato` の後の現在地は → /home/minato
  3. 状況判断: 同名ファイルが 2 つ。確実に指すには → 根からのパスで書く
- **実戦**（端）: 目的「/srv/app/config.txt を見つけて現在地をそこへ移す」。初期状態: /home/learner にいる。
  達成条件: 現在のディレクトリが /srv/app。ヒント: ① 今どこかを確かめる ② cd は住所へ歩く ③ `cd /srv/app`。
  想定エラー: `No such file or directory` → 原因候補「綴りの誤り」「相対パスと絶対パスの取り違え」
- **結果**: 成功「根からの住所で一度で移れた」／失敗「どこで道を外れたか」を木の図で示す
- **まとめ**: ① ファイルは木の中の住所で指す ② / が根 ③ pwd で現在地、cd で移動。次: linux.b.01

## linux.i.01 サービスと systemd（Linux / サービス）

- **解説**: 何か「裏で動き続けるプログラム（サービス）と、その管理役 systemd」。なぜ「再起動後に自動で動かし、落ちたら立て直すため」。
  何に「Web サーバ・DB などの常駐」。場面「サーバを再起動したら Web が止まっていた」
- **理解**: 状態の図（active・inactive・failed）に今の状態を当てる（図）／「起動」と「有効化」の違いを 2 択（簡単な確認）
- **クイズ**: 用語理解（enable の意味）／状況判断（再起動後に止まる → 有効化されていない）／原因特定（failed の手掛かりはどこ → status とログ）
- **実戦**（端）: 目的「web サービスを動かし、再起動後も動くようにする」。初期: 停止・無効。
  達成条件: active かつ enabled。ヒント: ① 状態を確かめる ② 動かすと、自動で動かすは別 ③ `systemctl enable --now web`。
  想定エラー: 設定の誤りで failed → 原因候補「設定ファイルの綴り」「ポートの使用中」→ journalctl を勧める
- **結果**: 再起動の模擬をして、動き続けることを見せる
- **まとめ**: ① start は今、enable は次回から ② status で状態 ③ 失敗はログ。次: linux.i.02

## net.b.06 名前解決（ネットワーク / DNS）

- **解説**: 何か「名前を IP アドレスに変える仕組み」。なぜ「人は数字を覚えられない」。何に「Web・メール・API の接続先」。場面「サイトが開かないが IP なら開く」
- **理解**: 問い合わせが端末 → 再帰問い合わせ → 権威サーバへ進む図を並べる（関係性）／「キャッシュ」の意味を結ぶ（用語）
- **クイズ**: 並べ替え（問い合わせの順）／原因特定（IP では繋がるが名前では繋がらない）／結果予測（dig +short の出力）
- **実戦**（端）: 目的「shop.example の IP を調べ、間違った設定を見つける」。初期: レコードが古い IP を指す。
  達成条件: 正しいレコードに直り、名前で繋がる。ヒント: ① dig で引く ② 期待と違う所 ③ A レコードを正しい値に
- **結果**: 名前で繋がった荷車が街を走る
- **まとめ**: ① DNS は名前と番号の対応表 ② dig で確かめる ③ キャッシュで反映が遅れることがある。次: web.b.01

## web.b.04 ステータスコード（Web / ステータス）

- **解説**: 何か「サーバの返事の種類を表す 3 桁の数」。なぜ「何が起きたかを機械も人も判断できる」。何に「障害の切り分け・API の処理分岐」。場面「画面が真っ白。何が起きた」
- **理解**: 2xx〜5xx の箱に例を仕分ける（図）／「4xx は誰の問題か」2 択（簡単な確認）
- **クイズ**: 用語理解（404 と 403）／状況判断（503 のとき最初に疑う所）／結果予測（存在しないパスへの curl）
- **実戦**（端）: 目的「3 つの URL のうち壊れているものを見つけ、原因を答える」。達成条件: 正しい組み合わせを提出。
  ヒント: ① curl -I で返事だけ見る ② 4xx と 5xx を分ける ③ 答えの組み合わせ
- **結果**: 原因ごとに都市の Web 施設のランプを直す
- **まとめ**: ① 4xx は頼み方、5xx はサーバ側 ② -I で見出しだけ ③ 次は原因の場所へ。次: web.b.05

## sec.b.07 証明書と認証局（TLS / セキュリティ / 証明書）

- **解説**: 何か「サーバが本物だと示す身分証（証明書）と、その発行者（認証局）」。なぜ「偽物のサイトに秘密を送らないため」。
  何に「HTTPS の相手確認」。場面「ブラウザに『安全ではありません』と出た」
- **理解**: サーバ証明書 → 中間証明書 → ルート証明書の連鎖を図で組む（関係性）／秘密鍵は誰が持つか（簡単な確認）
- **クイズ**: 並べ替え（連鎖）／原因特定（中間証明書が無いときのエラー）／用語理解（ルート証明書はどこにある）
- **実戦**（模）: 目的「警告の出るサイトを直す」。初期: 中間証明書が抜けている。達成条件: 連鎖が完成し、警告が消える。
  ヒント: ① 連鎖の図を開く ② 欠けている輪 ③ 中間証明書を配置
- **結果**: 鍵の印が付き、市民が安心して使う演出
- **まとめ**: ① 証明書は身分証 ② 連鎖でたどってルートに着けば信頼 ③ 秘密鍵は渡さない。次: sec.i.01

## git.b.06 衝突を解く（Git / conflict）

## ctr.b.01 コンテナとは（コンテナ / 考え方）

- **解説**: 何か「アプリと、動くのに必要な物一式を箱に詰めたもの」。なぜ「別の機械でも同じように動かすため（自分の PC では動いた問題）」。
  何に「配布・開発環境・スケール」。場面「同僚の PC でだけ動かない」
  - 状況説明: 開発者の PC では動くアプリが、ライブラリの版の違いで本番では動かない
- **理解**: アプリ・ライブラリ・設定・OS カーネルのうち箱に入る物を選ぶ（図）／「イメージ」と「コンテナ」を結ぶ（用語）
- **クイズ**: 用語理解（コンテナはカーネルを含むか）／状況判断（同じ環境を 10 台に）／結果予測（同じイメージから 3 つ動かすと）
- **実戦**（模）: 目的「依存の違いで動かない 3 台を、同じ箱で動かす」。達成条件: 3 台とも動く。ヒント: ① 何が違うか ② 箱に入れる物 ③ 箱を配る
- **結果**: コンテナ施設の港に箱が並ぶ
- **まとめ**: ① 箱ごと運べば同じに動く ② 設計図がイメージ、実体がコンテナ ③ Docker はこれを扱う道具の 1 つ。次: ctr.b.02

## docker.b.04 ポートを公開する（Docker / 公開）

- **解説**: 何か「コンテナの中の待ち受けを、外の入口に結ぶこと」。なぜ「コンテナは閉じた箱で、そのままでは外から届かない」。何に「Web を外に見せる」。場面「起動したのにブラウザで開けない」
- **理解**: 外のポートと中のポートの対応を図で結ぶ（図）／`-p 8080:80` の左右の意味（用語）
- **クイズ**: 結果予測（-p 無しで curl）／原因特定（ポートが使用中のエラー）／状況判断（2 つ目の Web を同じ機械で）
- **実戦**（端）: 目的「web を 8080 番で見えるようにする」。達成条件: 外から 8080 で応答。ヒント: ① ps で今の公開 ② -p 外:中 ③ `docker run -d -p 8080:80 web`
- **結果**: 箱に扉が付き、荷車が出入りする
- **まとめ**: ① 外:中 ② 同じ外ポートは 1 つまで ③ 繋がらないときは公開と待ち受けの両方を確かめる。次: docker.b.05

## k8s.b.05 Deployment（Kubernetes / Deployment）

- **解説**: 何か「『この Pod をいつも 3 つ』と宣言すると、数を保ち続ける仕組み」。なぜ「手で面倒を見ると、夜中の故障に間に合わない」。
  何に「止まらないサービス・更新・拡縮」。場面「Pod が 1 つ消えた」
  - 状況説明: 夜中にサーバが 1 台止まり、そこで動いていたアプリを人が手で別のサーバへ移す必要がある
- **理解**: あるべき数と現実の数を並べ、差を埋める動きを順に並べる（関係性）／Deployment・ReplicaSet・Pod の包含（図）
- **クイズ**: 結果予測（Pod を 1 つ消すと）／状況判断（数を 5 にしたい）／用語理解（宣言的）
- **実戦**（端）: 目的「web を 3 つで動かし、1 つ消して戻ることを確かめる」。達成条件: Ready が 3。
  ヒント: ① get pods ② delete して待つ ③ `kubectl delete pod <名前>` の後 `kubectl get pods`
- **結果**: クラスタ施設のビルの窓が 3 つ灯り、1 つ消えて、また灯る
- **まとめ**: ① 数を宣言すると保ち続ける ② 消えても作り直す ③ 数は scale で変える。次: k8s.b.06

## trouble.i.01 サーバの障害（トラブルシューティング / Linux）
