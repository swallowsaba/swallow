# 学習デザイン

何を教えるかは `docs/curriculum.md`、データの形は `docs/content-spec.md`、各レッスンの中身の設計は `docs/lessons/`。
この文書は**どう教えるか**を決める。

## 1. 教育方針

1. **用語を覚えさせる教材にしない。** 実際のエンジニアの動き「理解する → 操作する → 結果を見る → 問題を見つける → 原因を調べる → 直す → 確かめる」を身に付けさせる
2. **何のためかを先に伝える。** 何か・なぜ必要か・何に使うか・どんな場面で使うかを、操作より先に示す
3. **自由に学べて、迷わない。** どこからでも始められる。前提が足りないと思われるときは、基礎への道を示す（禁止はしない）
4. **失敗から学ぶ。** エラーは学習の材料。ゲームオーバーにしない
5. **実務につながる。** サーバ構築・ネットワーク設定・Web・Git・CI/CD・コンテナ・Kubernetes・セキュリティ・監視・障害対応など、実際の仕事の場面を題材にする
6. **一度で終わらせない。** 間隔を空けた復習で定着させる

## 2. レッスンの流れ（7 段）

```text
解説 → 理解 → クイズ → 実戦 → 結果・フィードバック → まとめ → XP / スキル
```

| 段 | 目的 | 必ず含めるもの | してはいけないこと |
|---|---|---|---|
| 解説 | 何か・なぜ・何に・どんな場面で、を伝える | 4 つの問いへの答え。図 1 枚以上。必要なら状況説明 | コマンドを打たせる。用語を説明なしで出す |
| 理解 | 読んだことが頭に入ったかを確かめる | 図・状況説明・簡単な確認・用語確認・関係性のどれか 2 つ以上 | 文章を読ませて終わる |
| クイズ | 使える知識になったかを確かめる | 1 レッスンに 3〜5 問。種類を混ぜる（下の「クイズ」） | 暗記問題だけにする |
| 実戦 | 自分で操作して結果を出す | 目的・達成条件・模擬環境・ヒント 3 段 | 安全でない操作を本当に実行する |
| 結果・フィードバック | 何ができ、何が足りないかを示す | 成功・失敗の理由、よかった手、改善の余地 | 点数だけを出す |
| まとめ | 要点を残す | 要点 3 つ以内・次に学ぶとよいこと・関連用語 | 解説の繰り返し |
| XP / スキル | 成長を見せる | 得た XP とスキルの変化、都市への影響 | XP だけを大きく見せる |

- 1 レッスンは 10〜20 分で終わる大きさにする
- どの段でも中断でき、再開できる（途中の状態を保存する）

## 3. 解説の作り方

- 4 つの問いに、この順で答える: **何か → なぜ必要か → 何に使うか → どんな場面で使うか**
- 例えを使ってよい（都市・郵便・工場など）。ただし例えの後に**正確な説明**を必ず続ける
- 図を 1 枚以上。図は SVG で、`docs/visual-design.md` の決まりに従う
- 状況説明（任意）: その技術が必要になる実際の場面を、図と短い文で示す。例: 同じ名前のファイルが 2 つあり取り違える → パスの必要性
- 解説の中では、用語を初めて出すところで必ず用語説明を付ける

## 4. 理解の作り方

文章を読ませて終わりにしない。次から 2 つ以上を組み合わせる。

- **図**: 図の一部を押して名前を答える / 流れの順番に並べる
- **状況説明**: 短い場面を示し「この場面で起きていることは」を選ぶ
- **簡単な確認**: はい・いいえ、または 2 択
- **用語確認**: 用語と説明を結ぶ
- **関係性**: 2 つの概念の関係（包含・順序・原因と結果）を選ぶ

理解の段は採点しない（XP も無い）。間違えたら、その場で解説の該当部分を示す。

## 5. クイズ

1 レッスンに 3〜5 問。**次の種類を少なくとも 3 種類混ぜる。**

| 種類 | 形 | 例 |
|---|---|---|
| 選択 | 選択肢から 1 つ / 複数 | 「ファイルの中身を表示するのはどれ」 |
| 状況判断 | 場面を示し、次にすべき行動を選ぶ | 「ディスクが一杯。最初に確かめるのは」 |
| 原因特定 | 症状とログから原因を選ぶ | 「Pod が Pending のまま。考えられる原因は」 |
| 結果予測 | 操作の結果を予測する | 「このコマンドを実行すると何行出るか」 |
| 用語理解 | 用語の意味・違いを問う | 「イメージとコンテナの違いは」 |
| 並べ替え | 手順を正しい順に並べる | 「TLS ハンドシェイクの順番」 |

- 誤答には必ず「なぜ違うか」を添える。正答にも「なぜ正しいか」を添える
- 選択肢の誤答は、学習者が実際に誤解しやすいものにする（でたらめな選択肢を置かない）

## 6. 実戦

- 題材: コマンド・ファイル操作・権限・プロセス・サービス・ネットワーク・Git・HTTP・Docker・Kubernetes・CI/CD・DB・トラブルシューティング
- **ブラウザで安全に実行できない操作は本物を実行しない。** 模擬環境を使う

### 6.1 実戦の原則（`REWORK-PRACTICE.txt`）

1. **本物の道具を使う。** その分野に本物のコマンドや操作があるなら、必ずそれを使う。架空の文を作らない
   - Git → git（git log・git revert・git restore・git switch など）/ Kubernetes → kubectl / Docker → docker / Linux・シェル → 本物のコマンド
   - Web・HTTP → curl / ネットワーク → ping・traceroute・dig・ip・ss / DB → SQL
   - 設定ファイルを書く物（Dockerfile・YAML・CI の設定・Web サーバの設定）→ 本物の書式で書く
2. **画面の操作は、打つコマンドが存在しない概念だけ。** コンピュータの仕組み・OSI の層・IaaS と PaaS の違い・責任共有モデル・構成図・流れの設計など
3. **画面の操作は、見て分かる形にする。** 文を打つ入力欄を作らない。操作は「ドラッグして置く」「ドラッグしてつなぐ」「ドラッグして並べ替える」の 3 つだけ。
   押すだけで済む物（選択・実行）はボタンでよいが、何をするボタンかが文字で分かること
4. **操作の結果を動きで見せる。** 置いたらその場で状態が変わる（色・形・数値が動く）。つないだら線を光の粒が流れる。並べ替えたら順に処理が進む様子が動く。
   失敗したら、どこで止まったかが赤く示される。動きを減らす設定では、動きを即時にする
5. **左の目的と右の画面が、見て結び付くこと。** 目的の文に出てくる物の名前が、右の画面にそのまま同じ名前で出ている

### 6.2 実戦の形

| 形 | 使う場面 | 実装 |
|---|---|---|
| 仮想端末 | シェル・Linux・Git・Docker・kubectl・curl・ネットワークのコマンド | 模擬エンジン（`src/engines/`）。既存のコードが要件を満たせば再利用する（`docs/decisions.md` D-05） |
| 設定の編集 | Dockerfile・Kubernetes の YAML・CI の設定・Web サーバの設定・ゾーンファイル | 画面の編集欄に本物の書式で書き、保存の後に本物のコマンドで確かめる |
| ブラウザ内演習 | SQL | ブラウザ内で動く SQLite（`docs/architecture.md`）で本物の SQL を実行する |
| 模擬環境 | 打つコマンドが存在しない概念（原則 2） | 状態を持つ模擬を、画面のドラッグで操作する。型は 4 つ（つなぐ・並べる・置く・読み取って答える。`docs/content-spec.md` 2.4.1） |

- 各実戦は「目的」「達成条件（状態で判定）」「初期状態」「ヒント 3 段」を持つ
- 判定は**出力の文字列ではなく、模擬環境の状態**で行う（ファイルがあるか、Pod が Running か、証明書が信頼されるか）
- **端末の実戦は、コマンドの実行の結果と模擬環境の状態で判定する。** 数える・探す・取り出す手順は、正しいコマンドを打って正しい結果が出た時点で達成する（`grep … | wc -l` で 3 が出た、`find` で場所が出た）。
  打った結果を、答えの欄に写させない。答えの欄は、コマンドでは得られない値（表やログを読み取って選ぶ・考える値）を答える時だけ使う（`docs/content-spec.md` 2.4）
- 最後のヒントは、そのまま打てば通る完全な答えにする。画面の操作の実戦は「何をどこへ置く・つなぐ・並べる」を日本語で書く

## 7. エラー学習

実戦でエラーが起きたら、必ず次の順で扱う。

```text
エラー → エラー内容（何と言われたか） → 原因候補（考えられる理由 2〜3 個） → ヒント → 再挑戦 → 成功
```

- エラーの画面は失敗の演出にしない。「調べてみよう」という調子で出す
- **エラーの案内は、コマンドが目的を果たせなかった時だけ出す。警告や、読めない場所を飛ばしただけの時は出さない。**
  本物のコマンドは、目的を果たしても標準エラーに文を出すことがある。赤い行が出たことだけでエラーにしない
  - 出さない: 終了の状態が 0（`curl -v` の途中経過、`kubectl` の `Warning:`、パイプの前の命令が出した文。パイプの終了の状態は、本物と同じく最後の命令の物）
  - 出さない: 結果（標準出力）が出ていて、エラーの行が全て「飛ばして続けた」物（`grep -r` や `find` の `Permission denied`。本物の grep はこの時 2、find は 1 を返すが、探した結果は出ている）
  - 出す: 結果が無い（`cat` で読めなかった）、または飛ばしたのでない失敗の文がある（`kubectl drain` が断った・`ssh-copy-id` の鍵が断られた）
  - 1 行に `;` `&&` `||` で並べた時は区切りごとに確かめ、どれかが目的を果たせなければ出す。後ろが `||` の命令の失敗は、その行の中で受けているので数えない
  - 答える欄の判定は、答えだけで決める。前に出た案内や端末の出力に引きずられない
  - 出さない: うまくいった、様子を見るだけの命令の出力（`git status` の「nothing added to commit」は、記録しようとした `git commit` の時だけ案内を出す。どの機械から調べたかで意味が変わる `nmap` の結果は、その機械から調べた時だけ。`docs/content-spec.md` 2.5 の `outputOf`）
- 最後のヒントの通りに打って出る案内は、その手順で想定した、本当に失敗した命令の物だけにする（衝突・拒否・届かないことを見せる手順。最後のヒントにも、そこで失敗すると書く）。
  言われたとおり打ったのに「エラー」と出て、何を間違えたのかと迷わせない（`docs/progress/verify-all.md` の C2）
- 見せるための失敗（手順の目的そのものが、その失敗を見て読むこと。`docs/content-spec.md` 2.4 の `designedErrors`）の案内は、見出しを「想定どおりのエラー。読んでみよう」、
  終わりの一言を「この手順は、このエラーを見て読むための物。読めたら、手順の目的の続きへ進もう。」にする。ほかの案内の「確かめたら、もう一度やってみよう。」（打ち直しを促す）は使わない。
  エラー内容・原因候補・次に確かめることは同じく出す（`docs/progress/verify-free.md` の【5】）
- 原因候補は、エラーの種類ごとにデータで持つ（`docs/content-spec.md` の `errorGuides`）
- エラーから自力で成功したことを記録し、トラブルシューティングのスキルと XP に反映する
- トラブルシューティング分野では、わざと壊れた状態から始める実戦を中心にする

## 8. 初心者への配慮

- 最初に遊ぶ人には「IT 基礎」の最初のレッスンを勧める（強制しない）
- 前提が足りない分野を開いたときは、推奨前提を示し、基礎の解説へ 1 回で飛べるようにする。**そのまま進むこともできる**
- 文章は短く。1 文 40 字前後を目安。1 画面の文章は 200 字以内
- 漢字の多い専門用語にはふりがなを付けられる（設定）
- 端末に慣れていない人向けに、実戦の入力欄の下に「今打てるコマンドの候補」を出せる（設定で消せる）。候補は、その実戦で使うコマンドの名前を全て出す（全ての手順の目的・ヒントの打つ行に出る物。パイプの後ろ・`sudo` や `ip netns exec 機械` の後ろも数える。今の手順の物を先に並べる）。打つ行そのものは出さない（`docs/progress/verify-all.md` の【6】）

## 9. 用語説明

- 全ての専門用語は用語集（`content/glossary/`）に載せる
- 各用語: 簡単な説明（1〜2 文）・なぜ重要か・関連する技術・関連する用語・関係するレッスン
- 本文中の用語は、初出で下線を付け、押すと説明が開く。**用語集に無い専門用語を本文に使うとテストで落ちる**
- 用語の説明にも例えを使ってよいが、例えだけで終わらせない

## 10. 推奨と自由

- 学習ライブラリでは全レッスンを開始できる
- 各レッスンの入口に「推奨前提」「関連」「難易度」「次に学ぶとよい」を表示する
- 推奨前提を学んでいない場合は「先に〇〇を見ておくと分かりやすい」と示し、「このまま始める」「先に〇〇を見る」を並べる
- 推奨学習順は `docs/curriculum.md` の通り。学習ライブラリの既定の並びにする

## 11. 復習

- レッスンの要点とクイズから、復習カードを作る
- 間隔（1 日・3 日・7 日・14 日・30 日）で復習を勧める
- 復習は都市画面のおすすめの欄と、施設の情報パネルから入れる
- スキル段階が定着度で下がると、その段階の説明（12 章）は出せなくなる。復習で戻る（罰ではなく知らせ。`docs/game-design.md` 4 章）

## 12. 都市の論点と学習（公聴会の「説明する」）

都市の仕組み（`docs/game-design.md` 17・20 章、`docs/decisions.md` D-20）の中で、学んだことを使う場。**学習そのものは何も変えない**（7 段の流れ・レッスンの中身・211 本の設計と 131 本の中身はそのまま）。

### 12.1 原則

- **ロックするのは「建てること」であって「学ぶこと」ではない。** 申請・審議・選挙・赤字・停電・落選は、どのレッスンを始めることも妨げない（指示書 15・17・53・60 章）
- **学んだことが、都市の論点に答える力になる。** 公聴会で出せる「説明する」の手は、その分野のスキル段階（`docs/game-design.md` 4 章）で増える
- **学ばなくても通せる道が必ず残る。** 譲歩と政治資本で通せる（`docs/content-spec.md` 6 章の検証）。説明は近道であって、関所ではない
- 公聴会の答えから XP は得ない（XP は学習だけから。`docs/game-design.md` 3 章）。説明は「学んだことを使う場」で、稼ぐ場にしない

### 12.2 スキル段階と出せる説明

| スキル段階 | 出せる物 | 中身の目安 | 例（データセンターの「冷却水の使用」） |
|---|---|---|---|
| 0 未修得 | 説明は出せない。譲歩と押し切るは出せる | — | 「クラウド 見習いで出せる説明が 1 つある」と示す |
| 1 見習い・2 初級 | 基本の説明 | 仕組みを正しく言い表す | 冷却の水は配管を回り続け、使い切るのは蒸発する分だけ |
| 3 中級 | 数字を示す説明（効きが大きい） | 測り方・比べ方・目標の値を示す | 使う電力と水を毎月測って公開し、効率の目標を決める |
| 4 上級・5 熟練 | 技術の代案の譲歩 | 損の小さい別の設計を出す | 外気で冷やす方式に切り替える |

- 段階ごとの効き（どれだけ反対が下がるか）は `docs/game-design.md` 17.2、データの形は `docs/content-spec.md` 7.1
- 説明の候補には、正しい物に混ぜて、**学習者が実際に誤解しやすい物**を置く（「クラウドなので建物で水は使わない」）。でたらめな候補は置かない（5 章のクイズの誤答と同じ規則）
- 候補の質は、選ぶ前には示さない。選んだ後に、住民と議員がどう受け取ったか（`why`）を 1 行で示し、誤り・一部の時は、なぜ足りないかと、学べるレッスンを示す。**正しい時も理由を示す**（5 章「正答にも『なぜ正しいか』を添える」と同じ）
- 誤った説明は、反対を少し強め、信頼を下げる（`docs/game-design.md` 17.2）。責める調子にしない（7 章のエラーと同じく「調べてみよう」の調子で、学べるレッスンへ案内する）

### 12.3 論点から学習へ

- 公聴会の論点ごとに「この論点を学ぶ」を出す（理由の `lessons`。`docs/ui-design.md` 10.3）。押すと入口の札（6 章の入口の札と同じ。推奨前提が未修了なら「先に見ると分かりやすい」を示すが、禁止しない）
- レッスンの間、都市の時間は止まり、公聴会は待つ。レッスンを終えて都市へ戻ると、同じ公聴会の窓に戻る。スキル段階が上がっていれば、新しく出せる説明がその場で並ぶ
- おすすめの欄（`docs/ui-design.md` 3 章）に、公聴会を待つ申請の論点に関係するレッスンを 1 つまで並べてよい（「審議中のデータセンターの論点: 冷却水の使用」）。推奨学習順（10 章）の物と並べ、どちらを選ぶかは学習者に任せる
- スキル段階が上がった時の知らせ（`docs/game-design.md` 10 章）に、新しく出せるようになった説明の論点を添える（何ができるようになったかを、都市の言葉で示す）

### 12.4 してはいけないこと

- 公聴会や選挙のために、レッスン・クイズ・実戦の中身を変える。都市の論点は `content/politics/` のデータに書き、レッスンの設計（`docs/lessons/`）は変えない
- 学習の進み（修了の数・XP）を、申請・選挙・公約の条件にする（`docs/content-spec.md` 7.7 の式に学習の語は無い）
- 公聴会の説明を、レッスンのクイズの代わりにする（説明は学んだことを使う場。理解を確かめるのはレッスンの 7 段）
