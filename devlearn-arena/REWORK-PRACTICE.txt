以後、この文書の決まりを基準とする。終わったら docs/progress/rework-practice.md に結果を記録しろ。

===========================================
【1】なぜ作り直すか
===========================================
今の実戦には 2 つの問題がある。

(a) 本物の道具が出てこない
  例: git.i.04（変更を取り消す）の実戦で打つのが「set version e19a5c3」という架空の文で、
  git コマンドが一度も出てこない。指示書 25 章「実戦ではコマンド・ファイル操作・Git・HTTP・
  Docker・Kubernetes などを扱う」と 52 章「実際のエンジニア業務につながる内容にする」に反する。

(b) 画面の操作が直観的でない
  欄に値を入れる・文を打つ形になっており、何をすればよいか見て分からない。
  ドラッグや動きで理解させる作りになっていない。指示書 23 章「図・状況説明を使い理解を確認する」に反する。

===========================================
【2】新しい決まり（原則）
===========================================
■ 原則 1: 本物の道具を使う
  その分野に本物のコマンドや操作があるなら、必ずそれを使う。架空の文を作らない。
  - git の実戦 → git コマンド（git log / git revert / git restore / git switch など）
  - Kubernetes → kubectl
  - Docker → docker
  - Linux・シェル → 本物のコマンド
  - Web・HTTP → curl
  - ネットワーク → ping / traceroute / dig / ip / ss
  - DB → SQL
  - 設定ファイルを書く物（Dockerfile・YAML・CI の設定・Web サーバの設定）→ 本物の書式で書く

■ 原則 2: 画面の操作は、打つコマンドが存在しない概念だけ
  本物の道具が無い概念（コンピュータの仕組み・OSI の層・IaaS と PaaS の違い・責任共有モデルなど）
  だけを画面の操作にする。

■ 原則 3: 画面の操作は、見て分かる形にする
  **文を打つ入力欄を廃止する。** 「文で操作する」の欄と「使える操作」のボタン列を全て消す。
  操作は次の 3 つだけにする。
  - ドラッグして置く（物を枠・場所へ運ぶ）
  - ドラッグしてつなぐ（点から点へ線を引く）
  - ドラッグして並べ替える（順番を入れ替える）
  押すだけで済む物（選択・実行）はボタンでよいが、何をするボタンかが文字で分かること。

■ 原則 4: 操作の結果を動きで見せる
  操作したら、何が起きたかが動いて見えること。
  - 物を置いたら、その場で状態が変わる（色・形・数値が動く）
  - つないだら、線を光の粒が流れる
  - 並べ替えたら、順に処理が進む様子が動く
  - 失敗したら、どこで止まったかが赤く示される
  prefers-reduced-motion のときは動きを即時にする。

■ 原則 5: 左の目的と右の画面が、見て結び付くこと
  目的の文に出てくる物の名前が、右の画面にそのまま同じ名前で出ていること。

【3】やること
===========================================
(1) content/lessons の全 131 本を調べ、実戦ごとに次を判定して docs/progress/rework-practice.md に表で書く
    - 本物の道具があるか（ある → 原則 1 で作り直す / 無い → 原則 2・3・4 で作り直す）
    - 今の形（terminal / sim-connect / sim-order / sim-assign / sim-config / sim-read / sql / editor）
    - 直した後の形

(2) sim-config（設定する）と、文で操作する入力欄を廃止する
    - sim-config の実戦は、本物の道具があるなら terminal か editor に作り直す
    - 本物の道具が無いなら、sim-assign（置く）・sim-connect（つなぐ）・sim-order（並べる）のどれかに作り直す
    - src/engines/sim から、文の入力で操作する経路を消す。ヒントの最後の「そのまま入れられる答え」は、
      端末の実戦ならコマンド、画面の操作なら「何をどこへ置く・つなぐ・並べる」を日本語で書く
    - テストで最後のヒントを再生する仕組みは残す（画面の操作と同じ関数を通す。文の入力欄は使わない）

(3) 画面の操作の 3 つの型を、ドラッグと動きで作り直す
    - sim-assign（置く）: 物の札をドラッグして枠に入れる。入れた瞬間に枠の状態が変わる。
      入らない物は枠が赤く光り、理由が 1 行出る
    - sim-connect（つなぐ）: 点から点へドラッグして線を引く。つながると光の粒が流れる。
      つながらない組み合わせは線が引けず、理由が出る
    - sim-order（並べる）: 札をドラッグして順番を入れ替える。並べ終えたら、上から順に処理が動いて見える。
      順が違うと、止まった所が赤くなり理由が出る
    - sim-read（読み取って答える）: 残す。ただし、答える前に画面の中の物を押すと、その部分が拡大・強調されること

(4) 分野ごとの実戦を、本物の道具で作り直す
    特に次を確かめる。git の実戦に git が、k8s に kubectl が、docker に docker が、
    web に curl が、net に ping/dig/ip が、db に SQL が、必ず出ること。
    既存の模擬エンジン（src/engines）に足りない機能があれば足す。足した機能は単体テストを書く。

(5) 仕様書を直す
    - docs/content-spec.md 2.4・2.4.1: sim-config を消し、3 つの型をドラッグの操作として書き直す。
      文の入力の形を消す
    - docs/ui-design.md 7・7.1: 右側の画面の作りを、ドラッグと動きの形に書き直す。文の入力欄を消す
    - docs/learning-design.md 6 章: 原則 1〜5 を書く
    - docs/lessons/ の 131 本の実戦の設計を、直した形に書き直す
    - docs/curriculum.md の表の実戦の記号を、直した形に合わせる

===========================================
【4】進め方
===========================================
- 一度に全部を作り直さない。分野ごとに進める。順は git → k8s → docker → linux → web → net → db →
  それ以外（found・ctr・cloud・sec・cicd・mon・devops・trouble・lab）
- 分野ごとに、画面を撮影して自分の目で確かめる。原則 3・4・5 を満たしているかを 1 つずつ見る
- 分野ごとに npm run typecheck と npm run lint と npm run test を通してコミットする
- 分野ごとの結果を docs/progress/rework-practice.md に追記する
- 全分野が終わったら ALLDONE とだけ出力して終われ
- 仕様書だけでは決められない事が出たら、docs/decisions.md の未決に「問題 → 影響 → 変更案」を書き、
  DECISIONNEEDED とだけ出力して止まれ
