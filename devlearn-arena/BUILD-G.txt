===========================================================================
市政の仕組みを実装する（G1〜G12）
===========================================================================

【0】何をするか

docs/development-plan.md の Phase G1〜G12 を、順に実装する。
仕様は既に決まっている（決着 D-20・docs/progress/gameplay-spec.md）。
この指示書は、進め方だけを定める。

読む順。

  1. CLAUDE.md（規則が全てに優先する）
  2. docs/decisions.md（D-20 と、未決があればそれ）
  3. docs/development-plan.md の G1〜G12
  4. docs/progress/phase-G<N>.md（あれば。どこまで終わったかの記録）
  5. その Phase に関わる仕様書

---------------------------------------------------------------------------
【1】1 つの Phase の進め方
---------------------------------------------------------------------------

1 つずつ。完成条件を満たすまで次へ行かない。

1. その Phase の「目的・実装対象・実装しないもの・完成条件」を読む
2. 先に失敗するテストを書く（CLAUDE.md 13 章）
3. 小さく実装する。大きな変更を一度に入れない（指示書 43・46 章）
4. npm run typecheck / npm run lint / npm run test /
   npm run content:check / npm run secrets
5. git push して、公開 URL
   （https://swallowsaba.github.io/swallow/devlearn-arena/）で確かめる。
   手元で npm run dev を動かす手順を書かない
6. 画面を撮って、自分の目で見る（tools/scenarios/）。
   docs/visual-design.md 8 章の視覚確認の項目と、
   docs/acceptance-criteria.md の V1〜V11・S1〜S29 のうち
   その Phase に関わる物を確かめる
7. docs/progress/phase-G<N>.md に記録する。
   何を作ったか・どう確かめたか・撮った画面・満たした完成条件・
   満たせなかった物とその理由
8. コミットして push する

意味のある単位でコミットする。1 つの Phase を 1 コミットにしない。

---------------------------------------------------------------------------
【2】Phase を通して守ること
---------------------------------------------------------------------------

### 2.1 乱数で決めない

反対率・支持率・議員の判断・投票率は、全て模擬の値から計算する
（docs/game-design.md 0 章）。乱数で埋めない。
同じ種から同じ結果になること（決定性）を、テストで固定する
（docs/testing-strategy.md 10 章）。

### 2.2 学習にロックを作らない

- 申請中・工事中・停電中の施設からも、学習を始められる
- どの分野も、いつでもどこからでも始められる
- スキルが 0 でも、譲歩と政治資本で申請を通せる道が必ず残る
- ミッションは申請にしない

docs/acceptance-criteria.md の S1〜S29 のうち、この項目は
各 Phase で毎回確かめる（後でまとめて確かめない）。

### 2.3 因果が見える

数字が動いたら、なぜ動いたかを平易な言葉で示せること。
「支持率が 6 下がった。主な理由は …」の形。

### 2.4 絵を変えない

決着 D-01 と docs/visual-design.md は生きる。
都市の絵・色・字を変えない。新しい画面は今の見た目の言葉で作る。

### 2.5 性能

tools/bench-sim.mjs で測る。見積もり（毎日 0.5ms 以下・
最も重い週 30〜60ms）を超えたら、その Phase の中で直す。
都市の画面の fps が落ちていないことを、Phase ごとに確かめる。

### 2.6 レッスンに触らない

content/lessons/・docs/lessons/・docs/curriculum.md を変えない。
G7（学習との接続）で足すのは content/politics/ の側。
レッスンの中身を変える必要が出たら、理由を記録に書いてから変える。

---------------------------------------------------------------------------
【3】特に注意する Phase
---------------------------------------------------------------------------

### G1（都市の模擬）

ここが全ての土台。急がない。
住民・事業者・地価・家賃・雇用・税収・通勤の式を、
docs/game-design.md 13 章のとおりに作り、1 つずつ単体テストで固める。
版 4 への移行（版 3 の保存データを読めること）も、ここで通す。

### G3（許認可）

今ある台本とテストが、ここで壊れる。施設を置いたらすぐ建つ前提の
物を、この Phase の中で直す。

  tools/scenarios/loop.mjs
  tools/scenarios/verify-lesson.mjs
  tools/scenarios/verify-free.mjs
  tools/scenarios/verify-wrong.mjs
  e2e/ のうち、施設を置く物

直した後、node tools/scenarios/loop.mjs が通ることを確かめる。

### G4〜G9（content/politics/ の中身）

このゲームが面白いかどうかは、ここで決まる。
仕組みが正しく動いても、中身が平板なら退屈になる。

- 議員 7 人は、名前・経歴・重く見る論点・口ぶりを持たせる。
  7 人が同じ顔に見えないこと
- 反対の理由は、その分野の実務の論点そのものにする。
  「反対です」で終わらせない。何が困るのかを具体的に書く
- 説明の文は、学んだ人が「そう、それが言いたかった」と思える内容にする
- 請願・公約・記事は、読んで情景が浮かぶ文にする
- 同じ文言の使い回しを避ける

書いたら、自分で読み返す。退屈なら書き直す。

### G7（学習との接続）

このゲームの芯（指示書 61 章）。次を画面で確かめる。

- 反対の論点から、関係するレッスンへ行ける
- レッスンを終えて戻ると、出せる「説明する」の手が増えている
- スキル 0 のまま、譲歩と政治資本だけで同じ申請を通せる
- 学習の進みを、市政の条件にしていない

### G12（通しの確認）

- tools/scenarios/ の台本を全て直す
- verify-all.mjs・verify-free.mjs・verify-wrong.mjs・
  verify-drag.mjs・loop.mjs を、公開 URL に対して流し直す
- 1280x720 でも流す。常時の UI が 20% 以内であること
- 結果を docs/progress/phase-G12.md に、
  docs/progress/verify-all.md と同じ書き方の表で書く
- 不合格の画像は docs/progress/shots/ に置いてコミットする

---------------------------------------------------------------------------
【4】やってはいけないこと
---------------------------------------------------------------------------

- 完成条件を満たさないまま次の Phase へ進む
- 「動いた」だけで完成とする（指示書 60 章）
- 乱数で数字を埋める
- 学習にロックを作る
- 都市の絵・色・字を変える
- Permit Pending の UI・絵・コード・固有の意匠・名前を写す
- 仕様書に無い機能・画面を足す（CLAUDE.md 14 章）
- 手元で npm run dev を動かす手順を書く
- 秘密情報を置く

---------------------------------------------------------------------------
【5】進め方
---------------------------------------------------------------------------

  - docs/progress/phase-G<N>.md を読み、終わっていない最初の Phase から
    進める
  - 確認を求めず、止まるな
  - 仕様書だけでは決められない事が出たら、docs/decisions.md の未決に
    「問題 → 影響 → 変更案」を書いてコミットし、DECISIONNEEDED とだけ
    出力して終われ
  - G12 まで全部終わったら ALLDONE とだけ出力して終われ
